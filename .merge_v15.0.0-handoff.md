## CRITICAL: How Results Reach the LLM

This is the single most important architectural fact in this merge. Read carefully.

### Why `session.followUp()` is WRONG

`session.followUp(text)` races with user messages and may sit unprocessed indefinitely —
it does NOT guarantee an LLM turn fires in a deterministic order. **Do not use it for
mtuicontrol result delivery.**

### The correct mechanism: `ctx.scheduleInput(text)`

`scheduleInput` emits to `SCHEDULE_SLASH_CHANNEL` → `waitForIdle()` → `editor.onSubmit(text)`.
This is the **exact same path as the user hitting Enter** — deterministic, no race, same
proven path used by mcommand itself.

#### Implementation (`interactive-mode.ts`)

```typescript
// types.ts — added to InteractiveModeContext
scheduleInput(text: string): void;

// interactive-mode.ts — implementation
scheduleInput(text: string): void {
    this.#eventBus?.emit(SCHEDULE_SLASH_CHANNEL, text);
}

// interactive-mode.ts — constructor subscription (already existed for mcommand)
eventBus.on(SCHEDULE_SLASH_CHANNEL, data => {
    const command = typeof data === "string" ? data : null;
    if (command) void this.session.waitForIdle().then(() => {
        this.editor.onSubmit?.(command);
    });
});
```

`scheduleInput` fires AFTER the current turn ends (via `waitForIdle`) — no re-entrancy.

#### Master wiring (`builtin-registry.ts`)

```typescript
result = await handleMtuicontrol(
    command.args ?? "",
    // asyncFollowUp: triggers LLM turn — fires at counter=0 ONLY
    (text) => { runtime.ctx.scheduleInput(text); return Promise.resolve(); },
    // asyncDisplay: prints to "!" panel — NO LLM turn
    (text) => runtime.ctx.showStatus(text),

```

### `SlaveExecState` — two callbacks, two purposes

```typescript

    counter: number;

    display: ((text: string) => void) | null;
    // submit: called only at counter=0 → scheduleInput → triggers ONE LLM turn
    submit: ((text: string) => Promise<void>) | null;
}
```

| Callback | Source | Effect | When |
|----------|--------|--------|------|
| `display` | `asyncDisplay` → `ctx.showStatus` | Prints to "!" panel; becomes conversation context automatically | Every `exec_step_result` |
| `submit` | `asyncFollowUp` → `ctx.scheduleInput` | Fires `editor.onSubmit` after idle → triggers ONE LLM turn | `counter === 0` only |

**stop/exit/crash**: use `display` (not `submit`) for visibility; the sync result is
already delivered via `scheduleInput`.

### Counter protocol (per slave) — counter-from-slave

**CRITICAL: master NEVER tracks step count independently. Slave always knows its own queue.**

1. Any `exec` send → master sets `state.counter = 1` (just marks a response is expected)
2. Each `exec_step_result` arrives → `state.display(formattedResult)` immediately → `state.counter = result.remaining`
3. `state.counter === 0` → `state.submit?.("slave(s) responded")` → `scheduleInput` → triggers ONE LLM turn
4. Pipe close with `counter > 0` → also fires submit (pipe close = remaining 0)

Submit message: `scheduleInput("slave(s) responded")` → `waitForIdle().then(() => editor.onSubmit("slave(s) responded"))` → LLM sees "slave(s) responded" + all "!" output from step results.

### Step completion mechanism — quiet-period debounce

**Previous approach (WRONG):** `waitForIdle()` after a 200ms yield. Race condition for UI-only slash commands like `/mmemory recall` that never trigger agent events — `waitForIdle` would return immediately before any events fired.

**Current approach:** quiet-period debounce in `runStep`.

```typescript
// Declared before event handlers
let onEvent: (() => void) | undefined;

// ALL event handlers (session.subscribe + eventBus) call this after appending:
onEvent?.();   // resets the quiet timer on every captured event

// In the await block:
onEvent = () => resetQuiet(true);   // wired — future events reset to 1s quiet
setTimeout(resetQuiet, 0);          // 3s initial quiet (gives execution time to start)

// resetQuiet(extended?: boolean):
//   extended=true  → 1s quiet  (reset by an arriving event)
//   extended=false → 3s quiet  (initial / fallback)
//   when quiet period fires → finish() is called
```

**Why it works:**

| Scenario | What happens |
|----------|--------------|
| UI-only slash (e.g. `/mmemory recall`) | `showStatus` fires → `PIPE_TUI_OUTPUT_CHANNEL` → `onEvent()` → 1s quiet → `finish()` |
| LLM prompt step | Agent events fire continuously → `onEvent()` → 1s quiet after last event → `finish()` |
| Initial 3s | Gives async execution time to start before any events arrive |
| Long silence (e.g. `sleep` step) | 3s quiet period fires → `finish()` |

**`onEvent` in all handlers:** every `session.subscribe` handler and every `eventBus.on` handler calls `onEvent?.()` immediately after appending to `sec`. This ensures the timer resets on every captured event regardless of source.

### mcommand rules — CRITICAL behavioral rules

- **ONE `mcommand` per turn.** Multiple mcommands queue simultaneously and fire
  simultaneously when `waitForIdle` resolves → race conditions, duplicate sessions.
- **Stay silent after mcommand.** No bash calls, no log reads, no other tools.
  The follow-up text IS the feedback delivered via `scheduleInput`.
- **Do NOT check logs to see results.** The `scheduleInput` path delivers results
  as conversation context automatically.

## exec / interrupt Command Syntax

### Syntax
```
/mtuicontrol exec [id] <step1>|<step2>|...
/mtuicontrol interrupt [id]
```

Each step is `type:body:timeout` where `:timeout` (ms) is optional (default 60000).

### Step types
| Type | Body | Description |
|------|------|-------------|
| `prompt` | message text | Send a prompt to the slave LLM |
| `slash` | `/command` | Inject a slash command |
| `bash` | shell command | Run bash (included in context) |
| `bash_x` | shell command | Run bash (excluded from context) |
| `python` | python code | Run Python in shared kernel |
| `python_x` | python code | Run Python (excluded from context) |
| `keypress` | key sequence | Inject key(s) e.g. `<ESC>`, `<ESC><ESC>`, `<C-c>` |
| `sleep` | (ignored) | Wait N ms (timeout IS the wait duration) |

### Escaping
- `|` separates steps — escape as `\|` to include a literal pipe in a body
- `:` before the final numeric timeout is the delimiter — escape as `\:` for a literal colon in the body

### Example (T6 scenario: prompt a long task, wait for streaming to start, then cancel)
```
/mtuicontrol exec rpc-XXXX prompt:use bash to run\: sleep 30:35000|sleep:2000|keypress:<ESC><ESC>
```
Steps:
1. `prompt:use bash to run\: sleep 30` — sends prompt with 35s hard timeout; slave starts running `sleep 30`
2. `sleep:2000` — waits 2s (slave is now streaming)
3. `keypress:<ESC><ESC>` — sends ESC+ESC to cancel

### Interrupt
```
/mtuicontrol interrupt [id]
```
Aborts the current step and clears the slave's exec queue.

## Key Decisions

- **`scheduleInput` not `session.followUp` for result delivery**: `session.followUp` races with user messages; `ctx.scheduleInput(text)` emits to `SCHEDULE_SLASH_CHANNEL` → `waitForIdle().then(editor.onSubmit)` — fires deterministically after current turn ends, same path as user Enter.
- **`display` (showStatus) vs `submit` (scheduleInput) separation**: `display` fires for every step result → "!" panel, no LLM turn; `submit` fires only at `counter===0` → ONE LLM turn. This prevents one LLM turn per step.
- **`exec_step_result` dynamic sections**: `sections` is `Record<string,string>` — slave emits any labels it wants; master iterates `Object.entries(result.sections)`. Common labels: `llm_input`, `llm_output`, `error`, `tool_output`, `bash_visible`, `bash_invisible`, `eval_visible`, `eval_invisible`, `task_progress`, `task_lifecycle`. No fixed set enforced.
- **`handle` → `handleTui`**: v15.0.0 split `SlashCommandSpec`; our mmemory/mprune/mreview/mtuicontrol use `runtime.ctx` (TUI-only). All must use `handleTui`.
- **`settings.override` not `settings.set` for `--no-memory`**: `set()` persists to disk; `override()` is session-scoped only.
- **`mtuicontrol` must be builtin, not extension**: `SCHEDULE_SLASH_CHANNEL` only dispatches to builtin-registry. `pi.registerCommand` is unreachable from this path.
- **Always `build.cmd`**: outputs to `binaries/omp-aws-corp.exe`; `deploy.cmd` reads from there.
- **Binary verification = SHA256 hash**, not log timestamps or session PIDs.
- **exec queue lives on the slave**: master sends a step list once; slave runs steps sequentially with individual hard timeouts; master receives a labeled trace via `exec_step_result` frames. `interrupt` is a step type (not a separate RPC): when found in a batch, the slave aborts the current step, drains the queue, enqueues post-interrupt steps only, and emits `exec_step_result(stepType:"interrupt", remaining=N)`.
- **exec_enqueue + exec_step_result is the ONLY master↔slave protocol**: inject_key, inject_slash, exec_interrupt deleted. Every command (`keypress`, `command`, `interrupt`, `exec`) routes through `enqueueExec`. `stop` and `list` are master-only exceptions. One path → one event model → no dual-LLM-turn bugs.
- **counter-from-slave**: master sets `counter=1` on any exec send. Slave reports `remaining` in each `exec_step_result`. Master sets `counter = result.remaining`. When `remaining=0` → `scheduleInput("slave(s) responded")`. Pipe close with `counter>0` also fires submit. Master NEVER tracks step count independently — slave always knows its own queue.
- **Startup exec_step_result**: slave emits `exec_step_result(stepType:"startup", remaining:0)` immediately after full initialization under `--rpc-pipe`. Master initializes `SlaveExecState` with `counter=1` at spawn time, so the startup frame drives counter to 0 → `scheduleInput("slave(s) responded")` → initial LLM turn confirming the slave is alive.
- **Two stream rule**: `runStep` subscribes to BOTH `session.subscribe` (agent events: `turn_end`, `tool_execution_*`) AND `session.eventBus.on(...)` (TUI/task events: `PIPE_TUI_OUTPUT_CHANNEL`, `TASK_SUBAGENT_PROGRESS_CHANNEL`, `TASK_SUBAGENT_LIFECYCLE_CHANNEL`). These are non-overlapping — agent LLM events never flow through eventBus; TUI/task events never surface via session.subscribe. Cannot collapse to one.
- **Quiet-period debounce for step completion**: `waitForIdle()` had a race condition for UI-only slash commands (e.g. `/mmemory recall`) that never fire agent events — idle was reached before any events arrived. Replaced with `onEvent` callback + `resetQuiet`: 3s initial quiet (allows execution to start), 1s quiet after any event. Every `session.subscribe` and `eventBus.on` handler calls `onEvent?.()` after appending. When quiet fires → `finish()`.
- **Timeout ESC + 2s drain**: on step timeout, slave injects ESC then waits up to 2s for remaining events (tool_execution_end errors, task lifecycle) before emitting the step result. Prevents losing error context that arrives just after the timeout fires.
- **Suppress empty steps in display**: `onExecStepResult` only calls `state.display` when at least one section is non-empty. `sleep` genuinely has no output. `keypress` CAN produce output (full TUI pipeline — ESC triggers cancellation notice, Enter triggers submit, etc.); quiet-period captures whatever fires.
