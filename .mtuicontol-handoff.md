> ```

> ## error ##
> [status] No agent messages to copy yet.
> ## llm_input ##
> /copy
> ```

## 1. Overview

`mtuicontrol` is a corp extension that lets an OMP session (the **master**) spawn, drive, and observe additional OMP sessions (each a **slave**) over a private RPC pipe. It is exposed as the `/mtuicontrol` slash command and operated via the `mcommand` tool.

**Location:** `src/extensibility/extensions/m-mtuicontrol-extension.ts`

**Enable in both `o` and `ow` configs:**
```yaml
mtuicontrol:
  enabled: true
```
Without `enabled: true` the extension is not registered and `/mtuicontrol` is silently ignored.

## 2. Architecture

```
Master session (interactive, headed)
  │
  ├── /mtuicontrol spawn → PipeConnection.create()
  │       ├── createPipeServer()  ← TCP on Windows, Unix socket on Unix
  │       ├── spawns child: omp.exe ... --rpc-pipe <port>
  │       └── waits for child { type:"ready", pid }
  │
  ├── RpcPipeClient (extends RpcClient)
  │       └── RpcInjectClient (wraps RpcPipeClient)
  │               ├── enqueueExec(steps[])  → exec_enqueue  (interrupt is a step type, not a command)
  │               └── onExecStepResult()   ← filters onEvent for exec_step_result
  │
  ├── SlaveExecState per session:
  │       ├── counter: number          ← steps remaining
  │       ├── display: (text) => void  ← ctx.showStatus → "!" panel, no LLM turn
  │       └── submit: (text) => void   ← ctx.scheduleInput → triggers ONE LLM turn
  │
  └── Result delivery: ctx.scheduleInput(text)
          → SCHEDULE_SLASH_CHANNEL
          → waitForIdle().then(editor.onSubmit)   ← same path as user hitting Enter

Slave session (interactive, headed, --rpc-pipe <port>)
  │
  ├── main.ts: detects --rpc-pipe, starts TUI + runRpcMode() in parallel
  │
  ├── interactive-mode.ts (TUI)
  │       ├── SCHEDULE_SLASH_CHANNEL → waitForIdle → editor.onSubmit
  │       └── showStatus/showError/showWarning → PIPE_TUI_OUTPUT_CHANNEL → eventBus
  │
  ├── rpc-mode.ts (pipe side-channel)
  │       ├── connectToPipe(arg) → sends { type:"ready", pid }
  │       ├── forwards incoming frames to handleRpcInjectCommand / handleRpcExecCommand
  │       ├── registerExecOutputFn(output) → wires emitStepResult to pipe write
  │       ├── subscribes to PIPE_TUI_OUTPUT_CHANNEL → output({ type:"tui_output", level, text })
  │       └── streams all AgentEvents + exec_step_result + tui_output frames to master
  │
  └── input-controller-inject.ts
          └── injectCommand(text, ctx) → ctx.editor.onSubmit(text)   ← direct, no waitForIdle
```

### Key design decisions

- Master is the **server**, slave is the **client**. This avoids port-forwarding concerns and allows the master to create the server before the child even exists.
- Slave runs in **headed+pipe mode**: a real TUI renders in the child window, and a background RPC loop handles the side-channel simultaneously. Neither blocks the other.
- The `--rpc-pipe` argument is consumed in `args.ts` so it never falls through to the agent as an initial user message.
- Result delivery uses `ctx.scheduleInput` (not `session.followUp`) — see Section 2b for the critical explanation.

## 2b. Notification Mechanism (CRITICAL)

This section explains how the master delivers exec results back into the LLM conversation. Getting this wrong causes silent failures or race conditions.

### The WRONG approach: `session.followUp()`

```typescript
// WRONG — do not use this pattern
(text) => runtime.ctx.session.followUp(text)
```

`session.followUp` enqueues text for delivery in the next available processing slot, but it **races with user messages**. If the user types something before the follow-up is processed, the follow-up may sit unprocessed indefinitely or fire at the wrong time. It has no deterministic ordering with respect to editor state.

### The RIGHT approach: `ctx.scheduleInput(text)`

`scheduleInput` emits to `SCHEDULE_SLASH_CHANNEL`, which the interactive-mode constructor subscribes to. It waits for the session to be idle, then submits the text exactly as if the user typed it and hit Enter. Deterministic, no races.

**Implementation in `interactive-mode.ts`:**
```typescript
// In InteractiveModeContext (also declared in types.ts):
scheduleInput(text: string): void {
    this.#eventBus?.emit(SCHEDULE_SLASH_CHANNEL, text);
}

// Subscription wired in InteractiveMode constructor:
eventBus.on(SCHEDULE_SLASH_CHANNEL, data => {
    const command = typeof data === "string" ? data : null;
    if (command) void this.session.waitForIdle().then(() => {
        this.editor.onSubmit?.(command);
    });
});
```

So the full path is: `scheduleInput(text)` → `SCHEDULE_SLASH_CHANNEL` → `waitForIdle()` → `editor.onSubmit(text)` — the **exact same path as the user hitting Enter** after the current turn completes.

**How it is called from `builtin-registry.ts`:**
```typescript
// builtin-registry.ts (~line 2115)
result = await handleMtuicontrol(
    command.args ?? "",
    // asyncFollowUp: triggers LLM turn — fires at counter=0 ONLY
    (text) => { runtime.ctx.scheduleInput(text); return Promise.resolve(); },
    // asyncDisplay: prints to "!" panel — NO LLM turn
    (text) => runtime.ctx.showStatus(text),
);
// Sync result (spawn/stop/list/etc.) also delivered via scheduleInput:
runtime.ctx.scheduleInput(result!);
```

Both the sync result and the async exec-completion follow-up go through `scheduleInput`. `session.followUp` is not used anywhere in the mtuicontrol path.

### Slave side: `input-controller-inject.ts`

The slave submits steps using the same terminal path but **without** `waitForIdle`:

```typescript
// input-controller-inject.ts
export function injectCommand(text: string, ctx: InteractiveModeContext): void {
    void ctx.editor.onSubmit?.(text);
}
```

This is called directly because `runStep` executes in a **background loop** (not inside an existing `editor.onSubmit` call). There is no re-entrancy risk on the slave. The master needs `waitForIdle` because `scheduleInput` is called while a slash-command handler is still on the stack — calling `editor.onSubmit` immediately would be re-entrant. On the slave, `runStep` is already running asynchronously in the background, so the direct call is correct.

Both paths ultimately arrive at `editor.onSubmit(text)` — the same code path a human Enter press takes.

### `SlaveExecState` — per-session state on the master

```typescript
interface SlaveExecState {
    counter: number;
    // display: called for every exec_step_result → ctx.showStatus → "!" panel, NO LLM turn
    display: ((text: string) => void) | null;
    // submit: called only when counter reaches 0 → ctx.scheduleInput → triggers ONE LLM turn
    submit: ((text: string) => Promise<void>) | null;
}
```

- `display` = `asyncDisplay` arg = `ctx.showStatus`. Prints to the "!" status panel. Does not trigger an LLM turn. The panel output becomes conversation context automatically when the next LLM turn runs.
- `submit` = `asyncFollowUp` arg = wraps `ctx.scheduleInput`. Triggers exactly ONE LLM turn when the full exec batch completes.

### Counter protocol (updated)

Master **never** tracks step count independently. The slave always knows its own queue length and reports it.

- On exec enqueue: master sets `counter = 1` (any send → at least one result is coming)
- Each `exec_step_result` carries `remaining: number` = slave queue length **after** this step
- Master sets `counter = result.remaining` (NOT decrement)
- When `remaining = 0`: `scheduleInput("slave(s) responded")` fires LLM turn
- Pipe/socket close with `counter > 0`: treated as `remaining = 0`, fires submit

### `onExecStepResult` handler in `m-mtuicontrol-extension.ts`

```typescript
// At spawn time, after client is set up:
client.onExecStepResult(result => {
    const state = slaveExecStates.get(id);
    if (!state) return;

    // Format all non-empty sections for display
    const parts: string[] = [];
    for (const [key, val] of Object.entries(result.sections)) {
        if (val) parts.push(`[${id}:step:${result.stepIndex}:${key}]\n${val}`);
    }
    if (parts.length > 0) state.display(parts.join("\n"));

    state.counter = result.remaining; // set from slave, NOT decrement
    if (state.counter === 0) {
        void state.submit?.("slave(s) responded");
    }
});

// exec enqueue case (m-mtuicontrol-extension.ts):
if (state) state.counter = 1; // always 1 until slave reports remaining

// onExit / pipe close:
if (exitState && exitState.counter > 0) {
    void exitState.submit?.("slave(s) responded"); // pipe close = remaining 0
}
```

## 3. Pipe Transport (`pipe-transport.ts`)

```
Windows: TCP loopback
  createPipeServer() → net.createServer() → listen(0, '127.0.0.1')
  childArg = String(port)          ← passed as --rpc-pipe value
  connectToPipe(arg) → parseInt(arg) → net.connect(port, '127.0.0.1')

Unix: domain socket
  createPipeServer() → net.createServer() → listen(/tmp/omp-rpc-<id>.sock)
  childArg = socket path
  connectToPipe(arg) → net.connect(sockPath)
```

**Why TCP on Windows:** Bun's Windows named-pipe server is broken (issues #11820, #13042, #14329 — both backslash and forward-slash paths fail server-side). TCP loopback is functionally equivalent for single-machine IPC.

**Wire format:** newline-delimited JSON (`\n`). Each frame is one JSON object per line. The `wrapSocket()` helper handles buffering and malformed-frame skipping.

**Handshake:**
1. Master calls `createPipeServer()`, gets `{ childArg, waitForClient, close }`.
2. Master appends `--rpc-pipe <childArg>` to the spawn command.
3. Slave starts, calls `connectToPipe(arg)`.
4. Slave sends `{ type: "ready", pid: process.pid }`.
5. Master's `_onReadyFrame` captures `childPid`.
6. From this point: all RPC frames flow bidirectionally. Master sends commands; slave sends responses and event frames.

**15s timeout:** `PipeConnection.create()` races `waitForClient()` against a 15s deadline. If the child never connects (crash, wrong args), the error surfaces immediately instead of hanging forever.

**`RpcTransport` interface** (`pipe-transport.ts`): abstraction over I/O channel. `PipeConnection implements RpcTransport`, injected into `RpcClient` as its second constructor argument. Keeps all pipe mechanics out of the client layer.

## 4. Exec Queue (`rpc-inject-handler.ts`)

The slave maintains a single `SlaveExecQueue` per session. The master sends steps as a batch via `exec_enqueue`; the slave processes them sequentially.

**`exec_enqueue`** — sent by master:
```typescript
{ type: "exec_enqueue", id: string, steps: RpcExecStep[] }
```
Handler: appends steps to `execQueue.steps`, starts the run loop if not already running. Returns `{ queued: N }`.

**`exec_interrupt`** — sent by master:
```typescript
{ type: "exec_interrupt", id? }
```
Handler: clears `execQueue.steps`, calls `execQueue.abort?.abort()` on the current step's `AbortController`. The current `runStep` promise resolves immediately via the abort signal listener. Returns success.

### `runStep` mechanics

Each step gets its own `AbortController`. For waited steps (`stepNeedsWait` = true):
1. Register `session.subscribe` listener for agent events **before** submitting — no race.
2. Register `eventBus.on` handlers for `PIPE_TUI_OUTPUT_CHANNEL`, `TASK_SUBAGENT_PROGRESS_CHANNEL`, `TASK_SUBAGENT_LIFECYCLE_CHANNEL`.
3. All handlers call `onEvent?.()` after appending to `sec`.
4. Set `setTimeout(timeoutMs)` hard timeout.
5. Register `abort.signal` listener.
6. Call `injectCommand(text, ctx)` → `ctx.editor.onSubmit(text)`.
7. Wire `onEvent = () => resetQuiet(true)`; start `setTimeout(resetQuiet, 0)` (3s initial quiet).
8. Quiet period fires (or timeout/abort) → `finish(reason)`: clears timers, unsubscribes, calls `emitStepResult(stepIndex, stepType, sections)`, resolves.

**On timeout**: ESC is injected first, then a 2s drain window waits for remaining events before `finish()` is called. This captures `tool_execution_end` errors and task lifecycle events that arrive just after the timeout fires.

For `keypress` and `sleep`: no subscription, no wait.

#### Two streams in `runStep`: output capture

> **TWO STREAMS — both required, non-overlapping:**
>
> | Stream | Source | What flows through it |
> |--------|--------|-----------------------|
> | `session.subscribe` | Agent session events | `agent_end`, `turn_end`, `message_update` (text_delta), `tool_execution_start`, `tool_execution_update`, `tool_execution_end` |
> | `session.eventBus.on(...)` | TUI/task bus events | `PIPE_TUI_OUTPUT_CHANNEL` (showError/showWarning/showStatus), `TASK_SUBAGENT_PROGRESS_CHANNEL` (⏳ spinner), `TASK_SUBAGENT_LIFECYCLE_CHANNEL` (subagent start/complete/failed) |
>
> **Cannot simplify to just the event bus.** Agent session events (LLM output, tool execution) do NOT flow through `eventBus` — they only surface via `session.subscribe`. TUI/task progress events do NOT surface via `session.subscribe` — they only flow via `eventBus`. Both subscriptions must coexist.

#### Startup handshake

When the slave is fully initialized under `--rpc-pipe`, `rpc-mode.ts` emits one `exec_step_result` frame with `stepType:"startup"` and `remaining:0`. The master initializes `SlaveExecState` with `counter=1` at spawn time. When the startup frame arrives, `counter` drops to 0 → `scheduleInput("slave(s) responded")` fires the initial LLM turn, confirming the slave is alive.

`ExecStepResult.stepType` union now includes `"startup"` (alongside `RpcExecStep["type"] | "interrupt"`).

### `exec_step_result` frame (slave → master)

Slave sends **one frame per step**. `sections` is a **dynamic `Record<string,string>`** — slave may emit any label; master iterates `Object.entries(sections)`:

```typescript
type ExecStepResult = {
    type: "exec_step_result";
    stepIndex: number;
    stepType: RpcExecStep["type"] | "interrupt";
    /** Steps still pending in slave queue AFTER this one. Master sets counter = remaining. 0 = all done. */
    remaining: number;
    /** Dynamic — any string key; master iterates Object.entries(sections). */
    sections: Record<string, string>;
};
```

**Common labels** (slave uses these; master accepts any key):

| Label | Source |
|-------|--------|
| `llm_input` | Text sent to LLM (prompt steps) |
| `llm_output` | LLM response text (turn_end) |
| `error` | showError/showWarning/showStatus from slave TUI |
| `tool_output` | LLM tool execution results (ToolExecutionComponent) |
| `bash_visible` | `!cmd` output, included in context |
| `bash_invisible` | `!!cmd` output, excluded from context |
| `eval_visible` | `$code` output, included in context |
| `eval_invisible` | `$$code` output, excluded from context |
| `task_progress` | TASK_SUBAGENT_PROGRESS_CHANNEL (⏳ spinner lines) |
| `task_lifecycle` | TASK_SUBAGENT_LIFECYCLE_CHANNEL (subagent start/complete/failed) |

Only populated sections are present in the frame. `sleep` always sends an empty frame (pure delay, nothing to collect). `keypress` MAY produce output — it goes through the full TUI input pipeline and can trigger any response (ESC shows cancellation, Enter submits, etc.); the quiet-period will capture whatever the TUI emits.

**Slave `StepSections`** is `Record<string, string[]>` with an `append(section, label, text)` helper that accumulates lines per label. `sectionsToResult()` converts to `Record<string,string>` by joining each array with `\n`.

### How `exec_step_result` flows from slave to master

```
1. Slave runStep calls emitStepResult(stepIndex, stepType, sections)
   — remaining = execQueue.steps.length (live queue length after this step)
        ↓
2. emitStepResult calls execOutputFn({ type: "exec_step_result", stepIndex, stepType, remaining, sections })
   — execOutputFn is the pipe write function registered by rpc-mode.ts
   via registerExecOutputFn(output)
        ↓
3. Frame serialized as JSONL, written over pipe
        ↓
4. Master RpcClient.#handleLine receives line, parses JSON
   "exec_step_result" is in agentEventTypes → dispatched to all onEvent listeners
        ↓
5. RpcInjectClient.onExecStepResult(listener) filters onEvent for type === "exec_step_result"
        ↓
6. m-mtuicontrol-extension.ts spawn handler:
   client.onExecStepResult(result => {
       state.display(formatted sections)  // → "!" panel
       state.counter = result.remaining;  // set from slave
       if (state.counter === 0) state.submit?.(...)  // → LLM turn
   })
```

### Look-ahead: concurrent step emission

When a look-ahead fires during a `prompt` step (e.g. sleep + keypress consumed concurrently while the prompt is running), the consumed steps emit their own `exec_step_result` frames with correct `remaining` values. Without this, master counter would go stale.

Example — `exec prompt:sleep 30:35000|sleep:2000|keypress:<ESC>`:
```
exec prompt:sleep 30:35000|sleep:2000|keypress:<ESC>
→ prompt starts; look-ahead sets 2s timer for sleep+keypress
→ at t=2s: sleep + keypress exec_step_result emitted; ESC injected
  (remaining after sleep = 1; remaining after keypress = 0 while prompt still running → BUT prompt is current step)
→ LLM processes, eventually aborted by ESC
→ prompt exec_step_result emitted with remaining=0
→ master counter=0 → scheduleInput("slave(s) responded")
```

`registerExecOutputFn(output)` is called in `rpc-mode.ts` immediately after the pipe connection is established, wiring the slave's step result emitter to the outgoing pipe write function.

### Step completion mechanism — quiet-period debounce

**Previous approach (replaced):** `waitForIdle()` after a 200ms yield. Race condition for UI-only slash commands (e.g. `/mmemory recall`) that never fire agent events — `waitForIdle` would return before any events arrived, completing the step before output was captured.

**Current approach:** quiet-period debounce in `runStep`.

```typescript
// Declared before all event handlers in runStep:
let onEvent: (() => void) | undefined;

// Every handler (session.subscribe + eventBus.on) calls this after appending to sec:
onEvent?.();  // resets the quiet timer on every captured event

// Wired in the await block just before waiting:
onEvent = () => resetQuiet(true);  // future events → 1s quiet period
setTimeout(resetQuiet, 0);         // start 3s initial quiet (no events yet)

// resetQuiet(extended?: boolean):
//   called with true  → arm 1s timer  (an event just arrived)
//   called with false → arm 3s timer  (initial / fallback)
//   when timer fires  → finish() is called
```

**Quiet period behavior:**

| Scenario | What happens |
|----------|--------------|
| UI-only slash (`/mmemory recall`) | `showStatus` fires → `PIPE_TUI_OUTPUT_CHANNEL` → `onEvent()` → 1s quiet → `finish()` |
| LLM prompt step | Agent events fire → `onEvent()` after each → 1s quiet after last → `finish()` |
| No events at all (e.g. `sleep` step) | 3s initial quiet period fires → `finish()` |
| Execution hasn't started yet | 3s initial quiet gives async dispatch time to enqueue first event |

**`onEvent` wired in all handlers:** every `session.subscribe` callback and every `eventBus.on` callback calls `onEvent?.()` immediately after appending content to `sec`. Sources:
- `session.subscribe`: `agent_end`, `turn_end`, `message_update` (text_delta), `tool_execution_start`, `tool_execution_update`, `tool_execution_end`
- `session.eventBus.on(PIPE_TUI_OUTPUT_CHANNEL)`: showError/showWarning/showStatus → `error` label
- `session.eventBus.on(TASK_SUBAGENT_PROGRESS_CHANNEL)`: ⏳ spinner → `task_progress` label
- `session.eventBus.on(TASK_SUBAGENT_LIFECYCLE_CHANNEL)`: subagent start/complete/failed → `task_lifecycle` label

## 5. TUI Output Pipe Forwarding

Slave TUI notifications (`showStatus`, `showError`, `showWarning`) are forwarded to the master. The flow has four hops:

```
Slave TUI (interactive-mode.ts)
  showStatus/showError/showWarning(text)
    → this.#eventBus.emit(PIPE_TUI_OUTPUT_CHANNEL, { level, text })

Slave RPC mode (rpc-mode.ts)
  eventBus.on(PIPE_TUI_OUTPUT_CHANNEL, data =>
    output({ type: "tui_output", level: data.level, text: data.text })
  )
    → written as JSONL frame over the pipe

Master RpcClient (rpc-client.ts)
  agentEventTypes includes "tui_output"
  → dispatched to all onEvent listeners

Master RpcInjectClient (rpc-inject-client.ts)
  onTuiOutput(listener) filters onEvent for type === "tui_output"
    → listener({ level, text })

Master mtuicontrol extension (m-mtuicontrol-extension.ts)
  client.onTuiOutput(ev =>
    state.display(`[slave:${ev.level}] ${ev.text}`)
  )
    → ctx.showStatus → printed to "!" panel, no LLM turn
```

**`tool_execution_end` forwarding:** `onEvent` also captures `tool_execution_end` frames. The result text is emitted as `[slave:tool:toolName] text` or `[slave:tool:error:toolName] text` via `state.display`.

**`turn_end` forwarding:** LLM response text from `turn_end` events is captured and emitted as `[slave:response] text`. Also stored in `sessionLastText` for the `prompt` command's fallback.

Note: `tui_output` forwarding is a secondary channel. For `exec` steps, the primary result delivery is `exec_step_result` frames (Section 4). `tui_output` carries incidental slave status messages.

## 6. Command Reference

> **Display-only vs LLM turn:**
> All operational commands (`spawn`, `stop`, `list`, `command`, `keypress`, `interrupt`) return `""` and deliver results via `asyncDisplay` → `ctx.showStatus` → "!" panel. **No LLM turn is triggered.**
> Only two commands trigger LLM turns:
> - `prompt`: response delivered via `scheduleInput("Child:\n...")` → one LLM turn
> - `exec`: `scheduleInput("slave(s) responded")` fires when `remaining=0` → one LLM turn when all steps complete

### `spawn`
```
/mtuicontrol spawn --cmd <full command line>
```
- User provides the complete command. `--rpc-pipe <port>` is appended automatically.
- On Windows, wrap in `cmd.exe /c` and use forward slashes. `start /WAIT ""` is injected automatically to keep `cmd.exe` alive until the child exits.
- Returns: `Session rpc-<id> ready. (child pid=NNNN)` — displayed via `asyncDisplay` ("!" panel only); **no LLM turn triggered**

### `prompt`
```
/mtuicontrol prompt [id] [--timeout N] <message...>
```
- Sends message, waits synchronously for full LLM response.
- `--timeout N` is in milliseconds; default 60000.
- On timeout: injects `<ESC>`, waits 3s for idle. If still stuck, terminates the session.
- Returns: `Child:\n<response text>` — delivered via `scheduleInput`, triggers one LLM turn.

### `keypress`
```
/mtuicontrol keypress [id] <ESC><CTRL-C>...
```
- Tokens between `<` and `>` are resolved to terminal escape sequences.
- Named keys: `ESC`, `ENTER`, `TAB`, `BACKSPACE`, `DELETE`, `UP`, `DOWN`, `LEFT`, `RIGHT`, `HOME`, `END`, `PGUP`, `PGDN`, `SPACE`, `F1`–`F12`
- Modifier combos: `CTRL-[A-Z]`, `CTRL-ALT-[A-Z]`, `CTRL-UP/DOWN/LEFT/RIGHT`, `ALT-UP/DOWN/LEFT/RIGHT`, `SHIFT-UP/DOWN/LEFT/RIGHT`
- Goes through `InputController.injectKey` → `Tui.simulateInput` → full TUI pipeline (real `onEscape`, etc.)
- Returns: `Injected N key(s).` — displayed via `asyncDisplay` ("!" panel only); **no LLM turn triggered**

### `command`
```
/mtuicontrol command [id] <slash command>
```
- Injects the slash command via `InputController.injectCommand` → `editor.onSubmit`.
- The slash command is handled at the TUI layer; the slave's LLM never sees it.
- TUI output (from `showStatus`/`showError`) arrives asynchronously as "!" panel output.
- Returns immediately: `Command "/cmd" scheduled.` — displayed via `asyncDisplay` ("!" panel only); **no LLM turn triggered**

### `exec`
```
/mtuicontrol exec [id] <step>[|<step>...]
```
Step format: `type:body[:timeoutMs]`

| Escape | Meaning |
|---|---|
| `\|` | literal pipe in body |
| `\:` | literal colon in body |
| `:<N>` at end | hard timeout in ms (default 60000) |

Step types and examples:
```
prompt:use bash to run\: sleep 30:35000
slash:/copy:5000
bash:echo hello\:world:5000
bash_x:sleep 30:35000
python:print(1+1):5000
python_x:import os; os.getcwd():5000
keypress:<ESC><ESC>
sleep:2000
```

Full T6 example:
```
/mtuicontrol exec prompt:use bash to run\: sleep 30:35000|sleep:2000|keypress:<ESC><ESC>
```

Returns immediately: `Enqueued N step(s) on rpc-<id>.`

**Acknowledgment behavior:** `exec` returns an empty string `""` → `scheduleInput("")` → `editor.onSubmit("")` → no-op (early return in `onSubmit`). The `Enqueued N step(s) on rpc-<id>.` message is shown via `asyncDisplay` (showStatus, "!" panel only). **No LLM turn is triggered on enqueue.** The LLM turn fires only when all steps complete (`remaining=0`).

Async follow-up (delivered via `scheduleInput("slave(s) responded")` after all steps complete). Sections are dynamic — master renders whatever labels the slave emitted:
```
[rpc-xxx:step:0:llm_input]
use bash to run: sleep 30

[rpc-xxx:step:0:llm_output]
I'll run that now...

[rpc-xxx:step:0:tool_output]
...bash output...

[rpc-xxx:step:0:task_progress]
⏳ Task: quick_task running...

[rpc-xxx:step:0:error]
...any showStatus/showError text...
```

The master LLM turn sees `"slave(s) responded"` as input plus all the "!" panel output from the step result frames.

### `interrupt`
```
/mtuicontrol interrupt [id]
```
`interrupt` enqueues `{ type: "interrupt" }` as a single exec step. The slave handles it **inline
during `exec_enqueue` parsing** — it is never pushed into the step queue.

**Slave-side action (in `handleRpcExecCommand`):**
1. Find `interrupt` in the incoming step batch.
2. Count steps before it in the batch + existing queue → `totalCleared`.
3. Clear `execQueue.steps`; call `execQueue.abort?.abort()` (kills any running step and its lookahead timer).
4. Push steps **after** the interrupt in the batch into the queue.
5. Emit `exec_step_result` immediately: `stepType="interrupt"`, `remaining = stepsAfter.length`.
6. If queue not running, call `runQueue(session)` for post-interrupt steps.
   If queue is running (abort still propagating), the `runQueue` finally block restarts automatically.

**Counter semantics — what remaining means:**
- `interrupt` alone → remaining=0 → LLM wakes immediately
- `exec interrupt|prompt|sleep` → remaining=2 → LLM wakes after prompt+sleep complete
- `exec prompt|interrupt` → prompt dropped, remaining=0 → LLM wakes immediately

**Lookahead timer safety:** the running step's abort signal is checked inside the setTimeout callback
(`if (abort.signal.aborted || done) return`) — so any scheduled sleep→keypress fires as a no-op.

### `stop`
```
/mtuicontrol stop [id]
/mtuicontrol stop --all
```
- `stop [id]`: stops one session (defaults to last used); result displayed via `asyncDisplay` ("!" panel only); **no LLM turn triggered**
- `stop --all`: stops all sessions; returns `Stopped N session(s).` or `No active sessions.` — displayed via `asyncDisplay`; **no LLM turn triggered**

### `list`
```
/mtuicontrol list
```
Returns active session IDs, one per line — displayed via `asyncDisplay` ("!" panel only); **no LLM turn triggered**

### ID routing
- `[id]` is optional on all commands except `spawn`.
- Defaults to `lastSessionId` (last spawned or used session).
- If `lastSessionId` is unset, falls back to the most recently added entry in `sessionPool`.
- Auto-cleanup: when a child exits, it is removed from the pool and `lastSessionId` is updated.

### mcommand rules (CRITICAL)

- **ONE `mcommand` per turn.** Multiple mcommands queue simultaneously and fire simultaneously when `waitForIdle` resolves → race conditions, duplicate sessions.
- **Stay silent after mcommand.** No bash calls, no log reads, no other tools. The follow-up text IS the feedback.
- **Do NOT check logs to see results.** The `scheduleInput` path delivers results as conversation context in the next turn.
