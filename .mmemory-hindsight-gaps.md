## LLM Roles

All LLM work in mmemory routes through the omp engine via the `executePython`
bridge in `ExtensionContext`. No external API keys needed. Two roles configured:

| Role | Config key | Purpose | Model characteristics |
|---|---|---|---|
| `memory` | `mmemory.modelRole` (default `"smol"`) | Reflect synthesis (foreground, user sees result); extraction when wired (Phase 3, background) | Fast, structured output; small context sufficient |
| `memory.consolidate` | `mmemory.consolidateModelRole` (default `"smol"`, Phase 3) | Consolidation batch pass, mental model seeding | Large context window; quality over speed; upgrade when Phase 3 implemented |

Both default to `smol` — zero extra cost in Phase 2. Split allows upgrading
`memory.consolidate` to a larger model for Phase 3 batch work without affecting
reflect throughput.

## What NOT to Copy from Hindsight

Hindsight's complexity is driven by HTTP round-trips to a cloud server. mmemory's
local-file model makes these patterns unnecessary or actively harmful:

- **Retain queue with debounce/batch/coalesce** — `fs.writeFile()` is synchronous and local. No queue needed. The `.md` files in `queue/` ARE the queue, deleted after build.
- **`observationScopes` / `strategy` / `updateMode`** — server-side processing directives with no meaning for local file writes.
- **Bank missions as server-side state** — mmemory's mission is a config string passed as a prompt parameter. The `.md` file header captures it per session.
- **Mental model TTL / delta modes / refresh-after-consolidation** — over-engineered for a manual-trigger system. mmemory's version: `/mmemory consolidate` writes files, extension reads at session start.
- **`retainBatch` semantics** — session overwrite model (fixed filename per session) makes batching irrelevant.

## The Dual-System Problem (Phase 3)

The extension (`mmemory-extension.ts`) and embedded tools (`MmemoryRetainTool`,
`MmemoryRecallTool`, `MmemoryReflectTool`) are two parallel systems that bypass
each other's state. Tools call `executeMemoryRecall` / `executeMemoryRetain` /
`executeMemoryReflect` in `tools/mmemory/index.ts` directly, without going through
the extension's session state (`lastRecallSnippet`, `lastRetainedTurn`, `turnCount`).

**The correct model:** extension owns all state; tools are thin dispatchers calling
into the extension's runtime. Deferred to Phase 3 (P3-6).

## Storage Layout

All mmemory files live under `storagePath` (default `D:/.ai/knowledge/projects`).
Each project gets a subdirectory; a reserved `global/` sibling serves cross-project
memories. Both follow the same internal layout.

```
knowledge/
  .gitignore                     ← * !.gitignore !README.md
  README.md
  projects/
    .gitignore                   ← * !.gitignore  (all project data private)
    omp_memory/                  ← storagePath/projectName
      .gitignore                 ← * (everything inside private)
      kb_config.yaml             ← auto-generated registry entry (type: external)
      queue/                     ← .md files drop here; DELETED after build
        (empty until first retain; YYYYMMDD-HHMMSS-<sessionId|note-id>.md at runtime)
      index/                     ← fully derived; safe to delete and rebuild
        .gitkeep                 ← tracks empty dir in git
        chunks.json              ← DURABLE STORE: full chunk texts (created on first build)
        vectors.safetensors      ← rebuildable from chunks.json (created on first build)
        vectors.meta.json        ← {model, count} for rebuild validation
      mental_models/             ← Phase 3: seeded summaries (empty until consolidation)
        .gitkeep
      facts.json                 ← Phase 3: extracted facts (does not exist yet)
      observations.json          ← Phase 3: consolidation output (does not exist yet)
    global/                      ← storagePath/global (per-project-tagged cross-project scope)
      .gitignore                 ← * (everything inside private)
      kb_config.yaml
      queue/
      index/
        .gitkeep
```

**Why .md files are deleted after build:**
`chunks.json` stores the full text of every chunk verbatim. After a build,
`chunks.json` contains everything needed for recall; `vectors.safetensors` is
rebuildable from it. Keeping `.md` files would be a redundant second copy.

**Build contract:**
1. `_run_build()` reads all `queue/*.md`, strips `---` separators, parses with `chunk_by_turns()`
2. Hashes each chunk; compares against hashes in `chunks.json` (no re-embed for known chunks)
3. New chunks embedded, appended to `chunks.json`, extended in vectors
4. Processed `.md` files deleted; `chunks.json` written atomically (temp → rename)

**`mmemory_update.py` — removed from binary:**
`ensureUpdateScript()` was never called; server handles all builds. File kept in
repo as a standalone CLI reference. Eliminates the chunking-logic divergence risk.

## Gap Details — Phase 2 Implemented

### #1 — Subagent guard (Gap 11) ✓
**Severity: High | Usability: Critical**

Added `taskDepth` to `ExtensionContext` (3 files: `types.ts`, `runner.ts`, `sdk.ts`).
`createSessionState()` returns `null` when `ctx.taskDepth > 0`, suppressing all
auto-retain and auto-recall for subagent sessions. Tool-initiated recall from
subagents still works (they get no extension state, but `executeMemoryRecall` is
stateless and always functional).

---

### #2 — Anti-feedback loop stripping ✓
**Severity: Critical | Usability: High**

`buildTranscript()` in `mmemory-extension.ts` now calls `stripMemoryInjections()`
on every message before including it. Strips `<memories>` and `<mental_models>`
tags. Mirrors Hindsight's `stripMemoryTags()` in `content.ts` (which strips four
legacy variants). Prevents the feedback loop where recalled memories get retained
as new content and surface in future recalls.

---

### #3 — Reflect synthesis framing (Gap 6) ✓
**Severity: High | Usability: High**

`executeMemoryReflect` now returns memories formatted as a synthesis task rather
than a raw recall list:
```
Project memory synthesis for: "<query>"
Mission context: <retainMission>

<recalled chunks with scores>

Based on the above project memories, synthesize a concise answer to: <query>
```

The calling LLM synthesizes from this context — the correct behaviour for an
inline tool. This is functionally equivalent to Hindsight's server-side `reflect`
LLM call; the difference is which LLM does the work (calling agent vs dedicated
reflect model). Phase 3 (P3-6 dual-system unification) enables a true server-side
call via `completeSimple` + `memory.consolidate` role when `modelRegistry` is cleanly
accessible on the tool path.

---

### #4 — `/clear` file deletion (Gap 12) ✓
**Severity: Medium | Usability: High**

`/mmemory clear` now filters `chunks.json` by date range or session ID, writes
atomically (temp → rename), deletes `vectors.safetensors` and `vectors.meta.json`
(they'll rebuild on next recall), then triggers a background build. The guard for
full-deletion-without-filter remains.

---

### #5 — Session dedup — fixed filename ✓
**Severity: High | Usability: Medium**

`sessionFilename(sessionId, sessionStartTime)` uses the session-start `Date` (set
once at `createSessionState()`) as the timestamp prefix. Repeated auto-retain calls
within one session overwrite `queue/YYYYMMDD-HHMMSS-<sessionId>.md` rather than
accumulating new files. Idempotency tested: 2-turn session → build → +1 turn →
exactly 1 new chunk embedded, 2 existing chunks reused.

---

### #6 — Turn-boundary chunking ✓
**Severity: High | Usability: Medium**

`chunk_by_turns()` replaces `chunk_markdown()` in `mmemory_server.py`. Each chunk
is one user+assistant turn pair — the question and its answer always co-located.
Long responses split at word boundaries with user message as context prefix on each
sub-chunk. Turn separators (`---`) stripped before parsing to ensure hash stability
across session overwrites.

**Companion fix — build coalescing:** `_pending_build: set[str]` replaces N waiting
threads with at-most-two sequential builds regardless of concurrent requests.

**Companion fix — H5 BM25 pruning:** `max(2, N*0.5)` threshold prevents over-pruning
at small corpus sizes (N=4: previously terms in 2+ docs were pruned; now requires
at least 2 docs before pruning activates).

---

### #7 — Directory-based global scoping (Gaps 7 + 10) ✓
**Severity: Medium | Usability: Medium**

`storagePath/global/` created automatically when `scoping === "per-project-tagged"`.
`executeMemoryRecall()` for `per-project-tagged` runs two parallel recall queries
(project dir + global dir), deduplicates by text prefix, re-ranks by score, slices
to `recallLimit`. Session auto-retains write to project dir only; tool-initiated
retains write to project `queue/` (global writes require explicit `global: true` in
Phase 3 after tags/routing are wired).

**This is cleaner than Hindsight's approach:** directory isolation is structural
(filesystem enforces it); Hindsight's tag-based approach requires every retain call
to set the correct tag or the memory lands in the wrong scope.

## Operational Improvements (Phase 2, not in original gap list)

### No visible console window ✓
`windowsHide: true` added to `Bun.spawn` in `server-client.ts`. Consistent with
all other background process spawns in omp (LSP servers, plugins, eval gateway,
git client). Server starts invisibly on first recall query.

### Background priority ✓
Two-level priority setting:
- **TypeScript** (`server-client.ts`): `process.setPriority(pid, 10)` — BELOW_NORMAL on Windows, nice ~10 on Unix. Corrects the previous `-5` (above-normal, backwards).
- **Python** (`mmemory_server.py` `main()`): `SetPriorityClass(BELOW_NORMAL_PRIORITY_CLASS)` on Windows, `os.nice(5)` on Unix. Sets the entire server process, not just the build thread.

### Logger integration ✓
`#consumeStderr()` in `server-client.ts` drains the Python stderr pipe and routes
each line through `logger.debug()` (or `logger.warn()` for `ERROR`-tagged lines).
All `[mmemory]` diagnostics — model load times, build stats, errors — now go to
the omp log facility and are never visible in the terminal.

### Privacy `.gitignore` ✓
`createSessionState()` writes two `.gitignore` files unconditionally (idempotent):
- `projectDir/.gitignore` → `*` — excludes everything inside the project
- `storagePath/.gitignore` → `*\n!.gitignore` — excludes all sibling project dirs

Conversation memory is never accidentally committed even if `storagePath` is inside
a git repository.

---

### `_run_build` zero-vector fix ✓
`_run_build()` step 5 `else` branch previously wrote zero-padded vectors for
existing chunks when `force_rebuild=True`, model changed, or `vectors_path`
was missing — all three paths produce zero vectors, which give garbage cosine
similarity scores on next recall. Fixed: `else` branch now re-embeds all chunks
(`existing_chunks + chunks_to_add`) using the same batched loop as the
corrupt-vectors fallback in the `if` branch. The `force_rebuild` action
(`/rebuild`) and model-change path now produce a fully valid index.

## Phase 3 — Implemented

All items shipped 2026-05-03. The "trigger" condition (30 sessions, quality
degradation) was a deferral gate — Phase 3 was implemented proactively.

### Gap 3 — LLM extraction ✓
**Severity: Critical (at scale) | Implemented**

`executeMemoryExtract(transcript, config, extractFn)` parses LLM JSON output
(`{fact, entities[], date}`), deduplicates case-insensitively against `facts.json`,
writes atomically. `loadFacts(config)` exported. `extractFromTranscript` fires
after each verbatim retain when `extractionMode === "structured"` (background,
fire-and-forget). Facts merged into recall with 1.2× score multiplier — precision
above raw chunks. `extractionMode` switched to `structured` in deployed configs.

### Gap 1 — Knowledge graph
**Eliminated from roadmap**

No concrete scenario demonstrated where a coding agent needs 1-hop entity expansion
that better recall query composition cannot handle. Eliminates NetworkX dependency,
`memory_graph.json` format, build step, and recall step. If multi-hop becomes a
real pattern, address it with recall query expansion in the prompt.

### Gap 4 — Consolidation / Gap 9 — Mental models ✓
**Severity: High (at scale) | Implemented**

One trigger (`/mmemory consolidate [--max-facts N]`):
1. `executeMemoryConsolidate`: reads `facts.json`, calls consolidation LLM via agent prompt, writes `observations.json` atomically. Observations merged in recall at 1.5× score (above facts, above chunks).
2. `executeMemoryMentalModelSeed`: seeds three built-in queries (`user-preferences`, `project-conventions`, `project-decisions`), writes `mental_models/<id>.md`.
3. Extension loads `mental_models/*.md` at session start → `<mental_models>` block appended to system prompt alongside `<memories>`.
`maxRawFacts` config key (default 100) controls the threshold check.
`/mmemory mm list` and `/mmemory mm regenerate` commands added.

### Recall query composition (P3-4) ✓
**Implemented**

`composeRecallQuery` and `truncateRecallQuery` ported from `hindsight/content.ts`,
exported from `index.ts`. `before_agent_start` and `session.compacting` both use
compose+truncate instead of `prompt.slice(0, 400)`. `retainContextTurns` default
flipped to 3. `recallMaxQueryChars` config key added (default 2000).

### Assistant message truncation (P3-5) ✓
**Implemented**

No `.slice(0, 1000)` cap was present on assistant messages — already clean.
`maxTranscriptChars` config key added (default 0 = unlimited); when > 0,
`buildTranscript` drops oldest turns first rather than truncating individual
responses.

### Dual-system unification (P3-6) ✓ (partial)
**Implemented — tool wiring deferred**

`getMmemorySessionConfig(ctx)` exported from `mmemory-extension.ts` so tools can
prefer the extension's already-loaded config over re-reading settings. Full tool
wiring (tools calling into extension state) deferred: `ToolSession` has no
`ctx: ExtensionContext` field. TODO comments added to all three tool files.
True server-side `completeSimple` for reflect also remains deferred for the same
reason.

## Embedding Model Comparison

### mmemory: BAAI/bge-small-en-v1.5 via fastembed

| Property | Value |
|---|---|
| Dimensions | 384 |
| Parameters | ~33M |
| MTEB average | ~58–60 |
| Storage per 1k chunks | ~1.5 MB |
| Inference | Local CPU, no network, no cost |
| Normalization | Mean pooling + L2, applied by fastembed wrapper |

### Hindsight default: text-embedding-3-small (OpenAI)

| Property | Value |
|---|---|
| Dimensions | 1536 (reducible via `dimensions` param) |
| Parameters | Proprietary |
| MTEB average | ~62.3 |
| Storage per 1k chunks | ~6 MB at full dimensions |
| Inference | API call — network latency, per-token cost, API key required |

### Assessment

**Quality gap is real but secondary.** text-embedding-3-small scores ~3–4 MTEB
points higher. bge-small-en-v1.5 handles exact- and near-paraphrase queries well,
which is the dominant pattern for session memory recall in a coding agent.

**Turn-boundary chunking (Phase 2 ✓) closes more of the quality gap than any
model upgrade would.** Coherent per-turn chunks produce better semantic centers
than 512-word windows spanning multiple topics. The model upgrade is a Phase 3
decision, deferred until extraction requires a full rebuild anyway.

**Upgrade path (Phase 3):** `BAAI/bge-base-en-v1.5` (768-dim, MTEB ~63.6) closes
most of the remaining gap at 2× storage/compute cost. Model change invalidates
all existing vectors — bundle with the extraction rewrite.

**Not recommended:** API embedding models add network latency to every build,
require subprocess API key management, and add per-token cost. Local model is
architecturally correct for an offline background process.
