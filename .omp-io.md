# OMP Input/Output Channel Map

> **Audience**: extension authors, skill designers, LLM agents working on this repo.
> Every mechanism that moves data into or out of OMP's TUI agent is described here:
> what renders, who sees it, whether a turn fires, and which function to call.

---

## Output channels in detail

### `showStatus(msg)` / `showWarning(msg)` / `showError(msg)`

**Source**: `modes/utils/ui-helpers.ts`

All three call `ctx.chatContainer.addChild(new Text(...))`. They never touch
`agent.#state.messages`. The LLM will never see them.

- `showStatus` — dim text; replaces the previous status line if two appear back-to-back
- `showWarning` — yellow text, same mechanism
- `showError` — red text; also clears any pending submission display

Use for real-time feedback during async operations. **Not** for anything the LLM needs to act on.

---

### `showMPanel(ctx, title, markdown)` — visual-only panel

**Source**: `utils/m-utils.ts` · section 5

Renders a `DynamicBorder` + title + `Markdown` block directly into `chatContainer`.
Explicitly documented as **"excluded from LLM context"** — it is purely visual.

```typescript
showMPanel(ctx, "Memory Recall — 'auth flow'", result.text);
```

Use for human-readable output: recall results, reflection summaries, memory views.
**Do not** use alone when the LLM also needs the content — pair with `appendCustomResult`.

---

### `appendCustomResult(session, customType, content)` — LLM-only injection

**Source**: `utils/m-utils.ts` · section 6

Calls `session.agent.appendMessage({ role: "custom", display: false, ... })`.
Pushes synchronously to `agent.#state.messages`. No render. No turn triggered.
`convertToLlm` maps `custom` role → `role: "user"` regardless of `display` flag,
so the LLM sees this verbatim on the **next turn**.

```typescript
appendCustomResult(session, "mmemory-recall", formattedResult);
```

**Important**: this alone does NOT wake the LLM. The content will be included
in the next turn that fires for any reason (user types, asyncSubmit, etc.).

**Pair with `showStatus`** for the dual-visible pattern:
```typescript
ctx.showStatus("recall: 5 memories found.");      // user sees immediately
appendCustomResult(session, "mmemory", formatted); // LLM sees on next turn
```

---

### `agent.appendMessage({display: true})` — LLM-visible + rendered

A `custom` message with `display: true` is both stored in message history (LLM
sees it) and rendered via `CustomMessageComponent` in the chat. Same path as
`appendCustomResult` but the UI renders it with a `[customType]` label and
markdown body. Useful when you want the user to see the content in a permanent
message (not ephemeral status text) AND the LLM to see it.

---

### System prompt injection — base vs per-turn

**Source**: `session/agent-session.ts`, `memory-backend/resolve.ts`

Two separate hooks, both on the `MemoryBackend` interface (`memory-backend/types.ts`):

**`buildDeveloperInstructions(agentDir, settings, session)`**
- Called during `rebuildSystemPrompt` inside `sdk.ts`
- Returns a string appended as `appendSystemPrompt` to `buildSystemPromptInternal`
- Becomes part of `#baseSystemPrompt` — baked in, rebuilt only when tool signature changes
- Use for: preambles, instructions on how to interpret injected memory tags

**`beforeAgentStartPrompt(session, promptText)`**
- Called on **every turn** in `#buildSystemPromptForAgentStart` (agent-session.ts:3385)
- Returns a string appended to `[...baseSystemPrompt, injected]`
- Receives the user's current prompt text — can do relevance-based recall
- Use for: per-turn memory injection (`<memories>`, `<observations>`, `<referenced_files>`)

Active backend is selected by `memory.backend` in `config.yml`.
`mmemory` backend is registered at `memory-backend/mmemory-backend.ts` (AWS-CORP addition).

---

### `BtwPanelComponent` — streaming async panel

**Source**: `modes/components/btw-panel.ts`

The only panel designed for streaming LLM output. Has states: `running` →
`complete` / `aborted` / `error`. Supports `appendText(delta)` for incremental
rendering. Footer line shows "Esc cancel /btw" during run, "Esc dismiss" after.
LLM output goes to the panel; user sees it; the main conversation is unaffected.

Used by the `/btw` command. Suitable template for any "side-channel LLM answer
while agent is idle" feature.

---

### Bash / Python execution components

**Source**: `modes/components/bash-execution.ts`, `modes/components/eval-execution.ts`

| Prefix | Renders | LLM sees | `convertToLlm` |
|---|---|---|---|
| `!cmd` | `BashExecutionComponent` (normal border) | ✅ as `role:"user"` | `bashExecutionToText(m)` |
| `!!cmd` | `BashExecutionComponent` (dim border) | ❌ | skipped (`excludeFromContext: true`) |
| `$code` | `EvalExecutionComponent` | ✅ as `role:"user"` | `pythonExecutionToText(m)` |
| `$$code` | `EvalExecutionComponent` (dim) | ❌ | skipped |

The dim border is the visual signal that output is excluded from context.

## Input channels / turn triggers

### `editor.onSubmit(text)` — main turn trigger

**Source**: `modes/controllers/input-controller.ts · setupEditorSubmitHandler()`

The primary entry point. Every submitted prompt goes through here.
Routes in order:
1. Empty during streaming → abort stream
2. `.` or `c` → empty agent continue (no text)
3. Extension `input` handler → may transform or consume
4. `executeBuiltinSlashCommand` → slash commands (`/`), returns `true` if consumed
5. `#invokeSkillCommand` → `/skill:name` commands
6. `!`/`!!` → `handleBashCommand`
7. `$`/`$$` → `handlePythonCommand`
8. Streaming active → `steer` path + `addToHistory`
9. Normal → `onInputCallback(submission)` + `addToHistory`

**History**: `editor.addToHistory(text)` is called by every branch that reaches the
agent. Slash commands now also call it (after the `slashResult === true` fix).

---

### `onInputCallback(submission)` — resolves the turn loop

**Source**: `modes/interactive-mode.ts · getUserInput()`

`getUserInput()` creates a `Promise` and stores the resolve function as
`this.onInputCallback`. Calling `onInputCallback(submission)` resolves it,
advancing the agent turn loop. This is the boundary between user input and
the session's `prompt()` call.

---

### `SCHEDULE_SLASH_CHANNEL` — deferred slash via event bus

**Source**: `modes/interactive-mode.ts` (listener), `utils/event-bus.ts` (constant),
`tools/mcommand.ts` (emitter)

```typescript
eventBus.emit(SCHEDULE_SLASH_CHANNEL, "/mmemory recall foo");
```

The listener in `InteractiveMode` calls `waitForInputReady().then(() => editor.onSubmit?.(cmd))`.
This defers execution until the agent is idle (not mid-turn). The command then
flows through `editor.onSubmit` as if the user typed it.

**Only available in TUI mode.** `MCommandTool.createIf()` returns `null` when
`session.eventBus` is absent (headless/ACP mode).

---

### asyncSubmit pattern — deferred LLM wake

**Source**: used in `builtin-registry.ts` (mtuicontrol handler)

```typescript
setImmediate(() =>
  ctx.session.waitForIdle().then(() =>
    ctx.editor.onSubmit?.(result)
  )
);
```

Used to wake the LLM after an async operation completes (e.g. after a slash command
has finished work and wants to inject its result as a follow-up turn).
`setImmediate` ensures the current microtask queue drains first.

---
### `steer` vs `followUp` — queued input during streaming

**Source**: `packages/agent/src/agent.ts`, `session/agent-session.ts`, `modes/controllers/input-controller.ts`

When the agent is already streaming a response, normal `editor.onSubmit` cannot
fire a new turn immediately. Instead, the message is queued in one of two independent
FIFO queues inside `Agent`:

| Mode | Queue | Delivery point | Keybinding |
|---|---|---|---|
| `steer` | `#steeringQueue` | After current tool call completes, **interrupts** remaining tools | Enter (while streaming) |
| `followUp` | `#followUpQueue` | After the agent is **fully idle** (no tools, no steering) | Ctrl+Enter (`app.message.followUp`) |

Both queues are drained inside `agent.ts · #runLoop()` — steering is checked after
every tool execution; follow-up is checked when the assistant has nothing left to do.

**How to send**:
```typescript
// interrupt mid-stream (user presses Enter while agent is running)
await session.prompt(text, { streamingBehavior: "steer" });

// politely queue — wait for the agent to finish first (Ctrl+Enter)
await session.prompt(text, { streamingBehavior: "followUp" });
```

**Skill commands** (`/skill:name`) also respect this: `#invokeSkillCommand` takes a
`streamingBehavior` parameter — Enter dispatches as `"steer"`, Ctrl+Enter as `"followUp"`.

**Display queue**: `session.enqueueCustomMessageDisplay(text, mode)` is the parallel
mechanism for the *visual* side — it shows the queued prompt in the pending-messages
area while it waits so the user can see what was queued. The display entry is
dequeued when the matching `message_start` event arrives from the agent.

**`pendingNextTurnMessages`** (different from both queues): a `CustomMessage[]` array
of "aside" messages injected at the start of the next turn regardless of streaming
state. Used for file mentions, goal context, plan context. Not an input channel —
populated internally by the session.

**Modes**: both queues support `"all"` (drain all at once) and `"one-at-a-time"`
(deliver one message per loop iteration). Controlled by `agent.setSteeringMode()` /
`agent.setFollowUpMode()`.

**Ctrl+C during streaming** clears both queues via `session.clearQueue()` —
returning `{ steering, followUp }` for display cleanup.

### Pending image input — `ctx.pendingImages`

**Source**: `modes/controllers/input-controller.ts · handleImagePaste()`
**Keybinding**: `app.clipboard.pasteImage` — default `alt+v` (Windows), `ctrl+v` (other)

Flow:
1. `readImageFromClipboard()` reads the system clipboard
2. Image validated/converted via `ensureSupportedImageInput`
3. Optionally resized via `resizeImage` (if `images.autoResize` is set)
4. Pushed to `ctx.pendingImages` array
5. `[Image #N]` placeholder inserted at cursor in the editor
6. On submit, `ctx.pendingImages` is included in the submission as `images: [...]`
7. Images are cleared from `pendingImages` after submission

The placeholder in the editor text is cosmetic only — the actual image data travels
via the `images` field in the submission, not embedded in the text.

## Script slots — `ctrl+alt+v` and other bindings

**Source**: `modes/controllers/input-controller-m-scripts.ts` (AWS-CORP)
**Config key**: `app.script.1` … `app.script.10`
**Default key**: none — must be configured in `config.yml` keybindings section

```yaml
# config.yml
keybindings:
  "app.script.1": "ctrl+alt+v"
```

Script slots execute a configured command and route output via the `@omp:` protocol.

### `@omp:` output protocol

Scripts communicate structured output via prefixed lines:

| Line format | Effect | LLM sees | User sees |
|---|---|---|---|
| `@omp:image:<path>` | Attach image as `[Image #N]` pending attachment | ✅ on submit | ✅ placeholder |
| `@omp:image:data:<mime>;base64,<data>` | Same, from inline data URL | ✅ on submit | ✅ placeholder |
| `@omp:text:<content>` | Insert text at cursor in prompt editor | — (not yet submitted) | ✅ in editor |
| `@omp:!!:<content>` | Show in chat with dim border, excluded from LLM | ❌ | ✅ |
| bare text | Submit as user message → fires a turn | ✅ | ✅ |

Any line not starting with `@omp:` is treated as bare text and submitted as a user
message. A script may emit multiple directives in one run. Text longer than 1000
characters is injected via bracketed-paste (treated as large paste by the editor).

**Runner prefixes for the command string:**
- `py: <code>` — runs in the live IPython kernel (stateful across calls)
- `js: <code>` — runs via `bun --eval` subprocess (stateless)
- anything else — spawned directly (whitespace-split args)

## `convertToLlm` role mapping

**Source**: `session/messages.ts`

`convertToLlm` maps every `AgentMessage` to an LLM `Message`. It does **not** filter
by `display` flag — only `excludeFromContext` on bash/python messages is a filter.

| `AgentMessage.role` | LLM `role` | Notes |
|---|---|---|
| `user` | `user` | passed through |
| `assistant` | `assistant` | passed through |
| `developer` | `developer` | passed through |
| `custom` | `user` | `display` flag ignored — always LLM-visible |
| `hookMessage` | `user` | same as custom |
| `bashExecution` | `user` | skipped if `excludeFromContext: true` (`!!`) |
| `pythonExecution` | `user` | skipped if `excludeFromContext: true` (`$$`) |
| `fileMention` | `user` | wrapped in `<system-reminder>...</system-reminder>` |
| `branchSummary` | `user` | rendered as text |
| `compactionSummary` | `user` | rendered as text, carries provider cache payload |
| `toolResult` | `toolResult` | content pruned by mprune |

**Key implication**: a `custom` message with `display: false` is invisible to the TUI
but the LLM sees it on the next turn. `display` is a rendering flag, not an LLM
visibility flag.

## Known issues in m-utils

**1. Section numbering collision** (`m-utils.ts`)

The file has two sections labelled `5`:
- `5. showMPanel` (line ~293)
- `5. resolveTemplateModelSpec` (line ~323, inserted later)

Section `6. appendCustomResult` follows. The duplicate `5` is cosmetic but
confusing when grepping for section numbers.

**2. `/mmemory recall` does not feed the LLM** (`slash-commands/builtin-registry.ts`)

`/mmemory recall` calls `showMPanel(ctx, ...)` but NOT `appendCustomResult`.
Result: the recall panel is visible to the user, invisible to the LLM.
When a skill instructs the LLM to `mcommand /mmemory recall`, the results
appear in a panel but the LLM receives nothing — the "output arrives as a
follow-up message" promise in the mcommand description is broken for this command.

Fix: add `appendCustomResult(runtime.ctx.session, "mmemory-recall", formattedResult)`
after `showMPanel` in the `recall` case. The LLM will then see the recall results
on the next turn without any turn being immediately triggered.

The `mmemory_recall` **tool** (used when LLM calls it directly) works correctly
because it returns a tool result — only the slash-command path is affected.

**3. `appendCustomResult` comment misleads about `display` flag**

The inline comment says "convertToLlm does not check the display flag, so LLM sees
content verbatim on next turn." This is accurate, but the inverse is easy to misread:
`display: false` does NOT mean LLM-invisible. It means UI-invisible. Any `custom`
role message — regardless of `display` — is always sent to the LLM via `convertToLlm`.
The `display` flag is purely a TUI rendering gate.
