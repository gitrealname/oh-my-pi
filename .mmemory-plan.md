## Five Tools  -  gateway + four direct

**`mmemory` (gateway)  -  user-triggered dispatch**
The LLM calls `mmemory` when the USER signals memory intent via any phrase.
- Trigger conditions in `mme-gateway.tool-desc.md`: `.memory`, `.mem`, `memory recall`, "check memory", "remember this", and any user phrasing that signals explicit memory intent
- The LLM infers the operation (recall/retain/reflect/consolidate) from context
- Dispatches to `/mmemory <operation> <query>` via `SCHEDULE_SLASH_CHANNEL`
- This is the exact mreview pattern: LLM calls tool -> tool emits slash command -> TUI executes
- Does NOT duplicate the direct tools  -  different caller: user direction vs agent autonomy

**Why not a `startsWith(".memory")` extension intercept:**
Exact prefix match is brittle. `.mem`, `memory recall`, mid-sentence, natural language equivalents all fail. The LLM handles all variants correctly because the gateway description teaches them. `mreview` itself has no extension intercept  -  100% LLM-driven.

**Four direct tools  -  autonomous LLM use**
Called by the LLM when it independently decides memory is relevant, without explicit user direction.

| Tool | Sidecar | When agent calls it |
|---|---|---|
| `mmemory` | `mme-gateway.tool-desc.md` | user says `.memory`, `.mem`, "check memory", "remember this", etc. |
| `mmemory_retain` | `mme-retain.tool-desc.md` | agent decides to store a decision or constraint |
| `mmemory_recall` | `mme-recall.tool-desc.md` | agent decides to retrieve context before acting |
| `mmemory_reflect` | `mme-reflect.tool-desc.md` | agent synthesises what is known about a topic |
| `mmemory_consolidate` | `mme-consolidate.tool-desc.md` | agent consolidates sessions into observations (expensive, sparingly) |

## Extension (`mmemory.ts`)  -  Lifecycle Only

The extension handles autonomous memory operations. Tools and slash commands are in the binary.

```ts
export function init(ctx: ExtensionContext): void {
  // Register lifecycle command (complements /mmemory binary slash cmd)
  ctx.registerCommand('mmemory-status', {
    description: 'Show mmemory lifecycle status (session state, last retain time)',
    handler: async (_args, context) => { /* show status from sessionMap */ }
  });

  ctx.on('session_start', async (session) => {
    const config = loadConfig(session.settings);
    if (!config || !session.settings.get('mmemory.enabled')) return;
    // Init storage (self-contained  -  no kb tools dependency)
    const state = new MmemorySessionState(config, session);
    sessionMap.set(session, state);
    await state.init();
  });

  ctx.on('before_agent_start', async (session, { prompt, systemPrompt }) => {
    const state = sessionMap.get(session);
    if (!state) return undefined;

    // No dot-command intercept here. All .memory / .mem / memory / implicit triggers
    // are handled by the LLM via mme-*.tool-desc.md condition lists.
    //
    // Why no startsWith intercept:
    //   - Brittle: exact string match misses "memory recall auth", ".mem", mid-sentence
    //   - Redundant: mreview itself has NO startsWith intercept  -  100% LLM-driven
    //   - Limiting: LLM can resolve "let .memory recall auth", ".mem auth", "memory!"
    //     from context; hardcoded prefix cannot
    //
    // The four tool descriptions (mme-recall/retain/reflect/consolidate.tool-desc.md)
    // each list their trigger conditions. The LLM calls the right tool. Same pattern
    // as mreview: LLM sees ".review" in prompt, calls mreview tool, tool emits
    // SCHEDULE_SLASH_CHANNEL. The tool is the bridge, not the extension.
    //
    // mme-gateway.tool-desc.md is the active sidecar for the mmemory gateway tool.

    // Await recall with deadline  -  fire-and-forget was wrong: the first turn (most important)
    // got no injection because lastRecallSnippet was always undefined on the first call.
    // recallDeadlineMs is the hard timeout; if exceeded, skip injection silently.
    const snippet = await Promise.race([
      state.recallForPrompt(prompt),
      new Promise<null>(r => setTimeout(() => r(null), state.config.recall.deadlineMs)),
    ]);
    return snippet
      ? { systemPrompt: systemPrompt.trimEnd() + '\n\n' + snippet }
      : undefined;
  });

  ctx.on('agent_end', async (session) => {
    const state = sessionMap.get(session);
    if (!state?.config.autoRetain) return;
    if (session.turnCount - state.lastRetainedTurn < state.config.retainEveryNTurns) return;
    void state.retain();  // fire-and-forget  -  vectorization is background
  });

  ctx.on('session.compacting', async (session, { messages }) => {
    const state = sessionMap.get(session);
    if (!state) return undefined;
    const result = await state.recallForMessages(messages);
    return result ? { context: result } : undefined;
  });

  ctx.on('session_shutdown', (session) => {
    sessionMap.get(session)?.dispose();
    sessionMap.delete(session);
  });
}
```

## Phase 1 Core: Parallel Retrieval

Parallel retrieval is **foundational**  -  everything else is built on top of it.
On every recall request, BM25 and semantic search run **concurrently** in the server
via Python threading. Results are merged via Reciprocal Rank Fusion (RRF) + recency boost.

```
recall(query)
+-- thread 1: embed query -> cosine similarity vs safetensors  [semantic]
+-- thread 2: tokenize query -> BM25 score vs bm25.json index  [keyword]
+-- join -> RRF merge -> apply recency exp(-age / recency_half_life_days[source] * weight) -> scope filter -> top-k
```

This is not optional or Phase 2. The architecture below (server + CLI) exists specifically
to make this fast enough for repeated user queries in a single session.

## Python Architecture: Server for Recall, CLI for Store

### Recall: `mmemory_server.py` (TCP server, warm model)

Pattern directly from `D:/.ai/scripts/semantic_server.py`:
TCP socket, line-delimited JSON, threading per client, idle watchdog, PID file.
**Reuse the base class pattern**  -  `mmemory_server.py` copies the server skeleton and
adds memory-specific actions.

Actions:
- `ping`  -  health check; returns port, PID, model_loaded, cached_kbs
- `recall`  -  parallel BM25+semantic, RRF merge, recency boost, scope filter, source filtering
- `build`  -  background thread: embed new chunks, dedup check, update safetensors+bm25.json
- `dedup_check`  -  cosine similarity check for a single embedding
- `shutdown`  -  graceful stop
- `bm25`  -  pure BM25 query against in-memory index, no vector; for callers that need keyword-only results or want to avoid model load (`{"action":"bm25","project_dir":"...","query":"auth.ts","limit":10}`)
- `vacuum`  -  trigger vacuum thread explicitly

Server lifecycle  -  **lazy start, auto-shutdown on idle:**
- **NOT started at session_start.** Started on first recall/build request.
- `MmemoryServerClient.query()` auto-starts the server if port is 0 or server is unreachable.
- Server prints `READY:<port>` to stdout; client reads it before sending the first request.
- `process.setPriority(proc.pid, -5)`  -  slightly elevated for recall responsiveness
- **Idle timeout: 10 min default** (`mmemory.serverIdleTimeoutMinutes`, configurable)
   -  server self-terminates via idle watchdog (same pattern as `semantic_server.py`)
   -  next query transparently restarts it (lazy-start handles this)
- On `session_shutdown`: server is NOT stopped. Extension removes session from `sessionMap`
  and cleans up local state only. Server stays alive for reuse by the next session.
  `stop()` is called only when `sessionMap.size === 0` (last session closed) or on explicit
  `/mmemory shutdown`. Idle timeout handles cleanup otherwise  -  avoids cold-start penalty
  for back-to-back sessions.

Key server internals  -  **fully self-contained, zero kb tool dependency:**
```python
import re, math, collections, threading, hashlib, json, os, socket, time
import numpy as np
from pathlib import Path
from fastembed import TextEmbedding
from safetensors.numpy import load_file as st_load, save_file as st_save

# -- Self-contained BM25 (no external deps, same algorithm as industry standard) --
def tokenize(text):
    text = re.sub(r'([a-z])([A-Z])', r'\1 \2', text)  # split CamelCase
    return [t.lower() for t in re.sub(r'[^a-zA-Z0-9]', ' ', text).split() if len(t) > 1]

def build_bm25_index(chunks):
    k1, b = 1.5, 0.75
    N = len(chunks)
    doc_tfs, doc_lengths, df = [], [], collections.Counter()
    for c in chunks:
        tf = collections.Counter(tokenize(c['text']))
        doc_tfs.append(tf); doc_lengths.append(sum(tf.values()))
        for t in tf: df[t] += 1
    avg_dl = sum(doc_lengths) / N if N else 1
    df = {t: c for t, c in df.items() if c < N * 0.5}  # prune high-freq terms
    return {'N': N, 'df': df, 'doc_tfs': doc_tfs, 'doc_lengths': doc_lengths,
            'avg_dl': avg_dl, 'k1': k1, 'b': b}

def bm25_search(index, query, top_k=10):
    k1, b, N, avg_dl = index['k1'], index['b'], index['N'], index['avg_dl']
    qterms = [t for t in tokenize(query) if t in index['df']]
    scores = []
    for i, (tf, dl) in enumerate(zip(index['doc_tfs'], index['doc_lengths'])):
        score = sum(
            math.log((N - index['df'][t] + 0.5) / (index['df'][t] + 0.5) + 1) *
            tf.get(t, 0) * (k1 + 1) / (tf.get(t, 0) + k1 * (1 - b + b * dl / avg_dl))
            for t in qterms if tf.get(t, 0) > 0
        )
        if score > 0: scores.append((i, score))
    return sorted(scores, key=lambda x: x[1], reverse=True)[:top_k]

# -- Server class --
class MmemoryServer:
    def __init__(self, port, timeout_minutes):
        self.model = None              # fastembed  -  loaded once on first recall
        self._vectors_cache = {}       # project_dir -> numpy array [N, 384]; swapped atomically under per-project lock
        self._bm25_cache    = {}       # project_dir -> BM25 index (in-memory); rebuilt from chunks.json after vacuum
        self._build_locks   = {}       # project_dir -> threading.Lock(); per-project, not global

    def _handle_recall(self, req):
        self._load_model()
        query = req['query']
        query_emb = np.array(list(self.model.embed([query]))[0])

        sem_results, bm25_results = [], []
        def run_semantic():
            vecs = self._load_vectors(req['vectors_path'])
            scores = cosine_similarity(query_emb, vecs)
            sem_results.extend(top_k(scores, req.get('limit', 10) * 2))
        def run_bm25():
            idx = self._load_bm25(req['chunks_path'])
            bm25_results.extend(bm25_search(idx, query, req.get('limit', 10) * 2))
        t1, t2 = threading.Thread(target=run_semantic), threading.Thread(target=run_bm25)
        t1.start(); t2.start(); t1.join(); t2.join()

        merged = rrf_merge(sem_results, bm25_results)
        # recency_half_life_days: the age (days) at which score is multiplied by exp(-recency_weight)
        # Parameterised per source type  -  scales with max_age_days[source] so the decay curve
        # is meaningful regardless of retention window. Default: max_age_days[source] / 4.
        for r in merged:
            age = (date.today() - date_from_path(r['path'])).days
            source = r.get('source', 'session')
            half_life = req.get('recency_half_life_days', {}).get(source,
                            req.get('max_age_days', {}).get(source, 365) // 4) or 90
            r['score'] *= math.exp(-age / half_life * req.get('recency_weight', 0.3))
        filtered = [r for r in merged if matches_scope(r, req['scope'], req['project'])]
        return {'results': filtered[:req.get('limit', 10)]}

    def _handle_build(self, req):
        def _do_build():
            with self._build_locks.setdefault(project_dir, threading.Lock()):
                pass  # os.nice set once at server __init__ / run()  -  not per-build (was cumulative)
                # chunk new .md files, update chunks.json, embed + dedup, update safetensors
                self._vectors_cache.clear(); self._bm25_cache.clear()
        threading.Thread(target=_do_build, daemon=True).start()
        return {'status': 'accepted'}
```

### TypeScript server client: `mmemory/server-client.ts`

```ts
import * as net from 'net';

// Singleton pattern  -  keyed by serverScriptPath.
// Both extension (lifecycle) and binary-side tools resolve the same instance.
// One server process per script path regardless of which call site reaches it first.
const _clients = new Map<string, MmemoryServerClient>();
export function getClient(scriptPath: string, config: MmemoryConfig): MmemoryServerClient {
  if (!_clients.has(scriptPath)) _clients.set(scriptPath, new MmemoryServerClient(scriptPath, config));
  return _clients.get(scriptPath)!;
}

export class MmemoryServerClient {
  private proc: ReturnType<typeof Bun.spawn> | null = null;
  private port = 0;
  private broken = false;

  constructor(
    private readonly serverScriptPath: string,
    private readonly config: MmemoryConfig,
  ) {}

  // Lazy-start: called before every query. Restarts transparently after idle timeout.
  // Startup deadlines: 30s cold start (model download), 5s warm reconnect.
  // On Python-not-found or model-load failure: logs warning, sets this.broken = true,
  // all subsequent query() calls return null immediately (recall skipped, not hung).
  private async #ensureRunning(): Promise<void> {
    if (this.broken) return;
    if (this.port > 0) {
      try {
        await withTimeout(this.#rawQuery({ action: 'ping' }), 5_000);
        return;
      } catch {
        this.port = 0; this.proc = null;  // dead  -  restart
      }
    }
    this.proc = Bun.spawn(
      ['python', this.serverScriptPath, '--port', '0',
       '--timeout', String(this.idleTimeoutMinutes)],
      { stdout: 'pipe', stderr: 'pipe' }
    );
    process.setPriority(this.proc.pid!, -5);
    try {
      this.port = await withTimeout(this.#readReadyPort(), 30_000);
    } catch (err) {
      const stderr = await readStderr(this.proc);
      const isPythonMissing = stderr.includes('No such file') || stderr.includes('not found');
      const msg = isPythonMissing ? 'Python not found' : `Server failed to start: ${err}`;
      console.warn(`[mmemory] ${msg}  -  recall disabled for this session`);
      this.proc.kill();
      this.broken = true;  // skip all future queries, don't re-attempt
    }
  }

  async query(action: string, args: Record<string, unknown> = {}): Promise<unknown | null> {
    if (this.broken) return null;
    await this.#ensureRunning();
    return this.#rawQuery({ action, ...args });
  }

  // Call once per session after server connects  -  drains queue files from any prior crash/timeout.
  async drainQueue(projectDir: string): Promise<void> {
    await this.query('build', { project_dir: projectDir }).catch(() => {});
  }

  #rawQuery(req: Record<string, unknown>): Promise<unknown> {
    return new Promise((resolve, reject) => {
      const socket = net.createConnection(this.port, '127.0.0.1', () => {
        socket.write(JSON.stringify(req) + '\n');
      });
      let buf = '';
      socket.on('data', d => { buf += d.toString(); });
      socket.on('end', () => { try { resolve(JSON.parse(buf)); } catch(e) { reject(e); } });
      socket.on('error', reject);
    });
  }

  async stop(): Promise<void> {
    if (this.port > 0) await this.#rawQuery({ action: 'shutdown' }).catch(() => {});
    this.proc?.kill();
    this.port = 0; this.proc = null;
  }
}
```

**Replaced by queue-only ingress:** TypeScript writes queue files, sends `{ action: "build" }`.
Server is the only writer to `chunks.json` + `vectors.safetensors`. If server is down, queue
files accumulate and are drained on next server startup (see `#ensureRunning` queue drain).

invariant  -  two code paths for one operation, doubled bug surface. One path, one writer.

**Orphaned server on process exit:** If omp exits abruptly, `session_shutdown` may not fire.
Python server stays alive until idle timeout (~10 min) then exits. ~500 MB RAM (fastembed)
held for that window  -  expected behavior, documented in README. Idle timeout is the safety net.

## `/mmemory clear`  -  Selective Date-Range Only

**Never deletes the full KB.** Requires `--from` and/or `--to` or `--session`.

```
/mmemory clear --from YYYY-MM-DD              from date onward
/mmemory clear --to YYYY-MM-DD                up to date (inclusive)
/mmemory clear --from DATE --to DATE          date range
/mmemory clear --session <sessionId>          one session's memories
```

Shows confirmation via `ctx.showHookConfirm(title, message)` (existing OMP TUI API  -  non-blocking).
`"Delete N chunks from DATE to DATE? [y/N]"`  -  user confirms before deletion.
Rebuild safetensors after deletion: Python via server's `rebuild` action or standalone  - 
load all, filter deleted chunk indices, save remainder. Self-contained.

## Architectural Correction  -  Queue-Only Ingress + Vacuum
*(added 2026-05-07  -  supersedes the facts.json / observations.json build-ingestion approach)*

### Storage Backend  -  Keep safetensors + numpy; keep homegrown BM25

**Decision: no library changes for vector search or BM25.**

**Vector search  -  safetensors + numpy brute force wins at mmemory's scale:**

| | safetensors + numpy | usearch HNSW |
|---|---|---|
| RAM (2000 chunks) | ~3 MB (raw vectors only) | ~4-5 MB (+30-40% graph overhead) |
| Query latency (1000 vectors) | ~0.5 ms | ~0.1 ms |
| Query latency (2000 vectors) | ~1 ms | ~0.15 ms |
| Vacuum rebuild | filter + save ~3 MB = ~50 ms | `remove(ids)`  -  faster, but... |
| Complexity | none  -  already working | new dep, explicit IDs in chunks.json |

HNSW only wins on speed at N > ~10,000-50,000. mmemory never reaches that.
Vacuum rebuild cost at mmemory's scale is ~50 ms, once per day  -  no visible impact.
safetensors uses less memory. Keep it.

**BM25  -  homegrown stays:**
In-memory rebuild from `chunks.json` on server start. At 2000 chunks: ~50 ms  -  negligible.
`bm25s` persistence would save this, but the rebuild is too fast to matter.
Homegrown BM25 is already correct and self-contained. No change.

**Filesystem layout per project (unchanged from current):**
```
<project_dir>/
  queue/              <- incoming .md files (session/fact/observation)
  chunks.json         <- all chunks with source/ts/text/metadata
  vectors.safetensors <- numpy float32 [Nx384], row-index aligned with chunks.json
  vacuum-state.json   <- last_vacuum_ts
  tmp/                <- temp files for in-progress vacuum (auto-cleaned on start)
```

**Vacuum filesystem scope:**
```
1. chunks.json         -> filter by (now - ts) > max_age_days[source]; write to tmp/; atomic replace
2. vectors.safetensors -> load; slice by surviving row indices; write to tmp/; atomic replace
3. tmp/*               -> delete anything older than 1 hour (interrupted vacuum artifacts)
```
Queue files are consumed on server startup  -  no orphan cleanup needed in vacuum.

**KB boosting unaffected:**
`kb_search.py` `_filename_boost()` (lines 402-416) multiplies `(score, index)` tuples
returned from `semantic_server`  -  blind to storage format. KB's `_semantic_search`
reads `data.vectors.safetensors` in the KB directory structure, a completely separate
path from mmemory's `vectors.safetensors`. No overlap, no impact.

**`VacuumWorker` input/output:**
- Input: `chunks_path`, `vectors_path`, `out_dir`, vacuum config
- Output: `(new_chunks_path, new_vectors_path)`  -  both written to `out_dir/tmp/`

### Problem with the previous implementation

`facts.json` and `observations.json` were client-side (TypeScript) write targets. With multiple
agents running in parallel, concurrent reads and writes to these shared mutable files are a race
condition  -  no file locking exists. The delete-and-replace in `_run_build` makes it catastrophic:
whichever build runs last silently overwrites the other agent's data.

### Invariant

**The server is the only process that writes to `chunks.json` and `vectors.safetensors`.**
The queue enforces this invariant. Every content type  -  sessions, facts, observations  -  reaches
the server as a queue file. The server serializes all writes through `self._build_locks[project_dir]`.

### Corrected ingress model

```
queue/<session-id>.md          source: session     (retainSession  -  existing, correct)
queue/<ts>-observations.md     source: observation  (/mmemory consolidate  -  FIX NEEDED)
```

`source: "file"` chunks are NOT queued as separate files. They are **derived by the build
step** from the `modified_files`/`written_files`/`read_files` arrays on session queue files.
For each unique path seen across all queue files, the build step upserts a `source: "file"`
chunk into `chunks.json` (update `ts` if path already exists, insert if new).

All three source types live in one unified `chunks.json` + `vectors.safetensors` index. (`source:fact` eliminated  -  consolidation now reads session chunks directly.)

### Queue file frontmatter schema (contract per source type)

All queue files are UTF-8 markdown with YAML frontmatter. The server's `_parse_frontmatter`
reads these fields. Unknown fields are ignored. Missing required fields cause the file to be
skipped with a logged warning.

**`source: session`** (written by `retainSession`):


### Vacuum  -  server-side age-based purge

All chunks have a `ts` field (epoch seconds). The server can purge stale chunks without any
client involvement. Age thresholds are configurable per source type  -  sessions live longest,
facts and observations are shorter-lived.

**New config keys (`mmemory.vacuum.*`):**

```yaml
mmemory:
  vacuum:
    enabled: true
    intervalHours: 24            # minimum hours between automatic vacuum runs
    sessionMaxAgeDays: 365       # source: session  -  long-term memory
    observationMaxAgeDays: 90    # source: observation  -  consolidated insights
    fileMaxAgeDays: 180          # source: file  -  file path chunks; 6 months default
```

**`MmemorySettings` / `MmemoryConfig`  -  `vacuum` block shape:**

```ts
// In MmemorySettings (settings-schema-m-extensions.ts)
vacuum: {
    enabled: boolean;              // default: true
    intervalHours: number;         // default: 24
    sessionMaxAgeDays: number;     // default: 365
    observationMaxAgeDays: number; // default: 90
    fileMaxAgeDays: number;        // default: 180
};


// Same shape reused verbatim in MmemoryConfig (index.ts)
// loadMmemoryConfig reads: settings.get("mmemory.vacuum.<key>") for each field
```

**`vacuum_config` payload sent from client to server in build request:**

```json
{
  "vacuum_config": {
    "enabled": true,
    "interval_hours": 24,
    "max_age_days": {
      "session": 365,
      "observation": 90,
      "file": 180
    }
  }
}
```

Server stores `vacuum_config` on first build request and reuses it for auto-triggered vacuums.
Vacuum purges chunks where `(now - ts) > max_age_days[source]`.
`source: "file"` chunks age independently from session chunks that reference the same paths.
**Architecture  -  thread, not subprocess:**

Vacuum runs as `threading.Thread(daemon=True)` inside the server process.
- Dies with the server  -  no orphaned processes, no race conditions
- No file IPC, no UUID signal files, no polling needed
- Thread has direct reference to server state; swap happens under per-project `_build_locks[project_dir]`

**Two files, clean separation:**
- `mmemory_vacuum.py`  -  `VacuumWorker` class, pure logic, zero server dependencies:
  - Input: `chunks_path`, `vectors_path`, `out_dir`, vacuum config dict
  - **Reads `chunks.json` once at startup into memory  -  original file untouched throughout**
  - Filters the in-memory copy: removes entries where `(now - ts) > maxAgeDays[source]`
  - Strips `read_files`/`modified_files`/`written_files` from entries older than `fileMetadataMaxAgeDays` (text kept)
  - Loads `vectors.safetensors` into a numpy array  -  original file untouched
  - Slices the array by surviving chunk indices  -  no re-embedding, pure numpy index filter
  - Writes filtered `chunks.json` + `vectors.safetensors` to NEW temp files in `out_dir`
  - Returns `(new_chunks_path, new_vectors_path)`  -  originals still live and serving
- `mmemory_server.py`  -  imports `VacuumWorker`, owns thread lifecycle:
  ```python
  def _run_vacuum(self, project_dir):
      dirs = self._dirs(project_dir)
      worker = VacuumWorker(dirs["chunks"], dirs["vectors"], dirs["tmp"], self._vacuum_config)
      new_chunks, new_vecs = worker.run()        # originals live throughout; only temp files written
      lock = self._build_locks.setdefault(project_dir, threading.Lock())
      with lock:
          os.replace(new_chunks, dirs["chunks"]) # atomic  -  chunks replaced first
          os.replace(new_vecs,   dirs["vectors"]) # then vectors
          # Tiny window between the two os.replace() calls: a cache-miss recall could read
          # new chunks.json but stale vectors.safetensors. Acceptable at this scale
          # (millisecond window). _invalidate() closes the gap for all subsequent calls.
          self._invalidate(project_dir)
      self._vacuum_thread = None
  ```

**BM25 note:** BM25 is always derived from `chunks.json` in memory  -  never persisted.
Vacuum filters `chunks.json`, server reloads BM25 from the new file on next recall.
Nothing to swap for BM25  -  cache invalidation is sufficient.

**Idle timeout suppression:**
```python
# Watchdog checks before self-terminating:
if self._vacuum_thread and self._vacuum_thread.is_alive():
    return  # vacuum is activity  -  reset idle timer
```

**Triggers:**
- (a) Automatic: end of `_run_build` if `intervalHours` elapsed since `last_vacuum_ts`
- (b) Explicit: `{"action":"vacuum","project_dir":"..."}` request
- Only one vacuum thread per project at a time  -  skip if already running

**`last_vacuum_ts`:** stored as a field in a small `vacuum-state.json` sidecar alongside
`chunks.json`. Written by the server after vacuum completes (not by the worker  -  worker is pure).

**`VacuumWorker` is pure and testable**  -  no server internals, no side effects beyond
writing to `out_dir`. Server handles all state mutations after `.run()` returns.

**Design decision: master flushes outstanding data then performs the atomic swap**
Before vacuum swaps the live DB files:
1. Master drains the queue (completes any in-flight build for the project)
2. Master acquires `_build_locks[project_dir]`
3. Master calls `os.replace()` for both files (chunks then vectors)
4. Master calls `_invalidate()` to flush in-memory caches
Only the master touches the live DB files. No other thread may write them.
GIL does NOT guarantee safe concurrent I/O -- the lock + master-only-writes does.

**Current implementation is TECH DEBT -- violates the above decision**
`_run_vacuum` (a daemon thread) currently calls `os.replace()` directly under the lock.
This is wrong: the vacuum thread is not the master, and no queue flush happens before the swap.
The queue accumulates new files during vacuum that are not flushed before the swap.
The `vacuum_start_ts` guard (handoff Phase 3) partially mitigates by merging chunks produced
during vacuum -- but this is a workaround for the missing flush, not a fix.
The two-`os.replace` calls (chunks then vectors) are also not atomic together.

**Correct fix (tracked in todo):**
- VacuumWorker returns `(new_chunks_path, new_vecs_path)` only -- no `os.replace` in worker
- Master receives paths, flushes queue (completes in-flight build), then under lock:
  `os.replace` both files, `_invalidate`
- No vacuum thread writes to live DB files at all

## System Prompt Injection Architecture

> Researched from source. Verified 2026-05-09.

### How content reaches the system prompt (OMP core)

```
sdk.ts rebuildSystemPrompt()
    |
    +-- resolveMemoryBackend(settings).buildDeveloperInstructions(agentDir, settings, session)
    |       +-- returns markdown string -> appendPrompt field
    |
    +-- buildSystemPromptInternal({ appendSystemPrompt: appendPrompt, rules, contextFiles, agentsMdSearch, ... })
            +-- Handlebars render of system-prompt.md or custom-system-prompt.md
                    +-- {{appendPrompt}}          <- memory backend output (shows in /dump)
                    +-- {{rules}}                 <- rulebook pipeline (path-glob matching)
                    +-- {{contextFiles}}          <- CLAUDE.md / AGENTS.md / context files
                    +-- {{agentsMdSearch}}        <- AGENTS.md dir-context listing
```

### Injection mechanisms  -  full taxonomy

| Mechanism | Who | Static/per-turn | /dump | Extension accessible |
|-----------|-----|-----------------|-------|---------------------|
| `{{rules}}` | Rulebook pipeline | Static, session start | Yes | No  -  baked into sdk.ts |
| `{{contextFiles}}` / `{{agentsMdSearch}}` | context-file.ts capability | Static, session start | Yes | No  -  baked into sdk.ts |
| `{{appendPrompt}}` via `buildDeveloperInstructions()` | MemoryBackend interface | Static, every prompt rebuild | Yes | Via MemoryBackend only |
| `MemoryBackend.beforeAgentStartPrompt()` | MemoryBackend interface | Per-turn (refreshes state) | No | Via MemoryBackend only |
| Extension `before_agent_start` -> `{ systemPrompt }` | Extension hook | Per-turn, replaces for that turn | No | Yes  -  any extension |
| `--append-system-prompt` / `appendSystemPromptFile` | CLI / main.ts | Static | Yes | No |
| `options.systemPrompt` (custom) | SDK caller | Static | Yes | No |

### There is NO generic extension mechanism for base system prompt injection

The only extension-accessible path into the base system prompt (the one shown in `/dump` and sent to the LLM on every call) is:
1. Implementing `MemoryBackend` and registering in `resolve.ts`  -  `buildDeveloperInstructions()` feeds `appendPrompt`
2. Being baked into `BuildSystemPromptOptions` in `sdk.ts`

The `before_agent_start` hook returning `{ systemPrompt }` is per-turn only  -  it replaces the prompt for that single turn and is NOT reflected in `/dump`.

### How mmemory injection works

```
session start
    +-- mmemory-backend.ts start()
    |       +-- loadMmemoryConfig()  -  config guard: if !enabled, return early (logged)
    |       +-- executeMemoryBuild() [void]
    |               +-- .then() -> getMmemorySessionState() -> consolidation poll -> pendingConsolidationChunks
    |
    +-- mmemory-extension.ts session_start  <- populates sessionMap (extension owns state)
            +-- executeMemoryBuild() [void, redundant  -  known issue, harmless]

per-turn: sdk.ts agent loop
    +-- backend.beforeAgentStartPrompt(session, promptText)
    |       +-- truncateRecallQuery(prompt)
    |       +-- executeMemoryRecall() -> TCP -> mmemory server -> BM25 + cosine
    |       +-- formatRecallForSystemPrompt() -> <memories>/<observations> blocks
    |       +-- state.lastRecallSnippet = snippet  <- stored in extension sessionMap entry
    |
    +-- backend.buildDeveloperInstructions(agentDir, settings, session)
            +-- getMmemorySessionState(session.sessionManager) -> reads extension state
            +-- state.lastRecallSnippet -> formatted recall
            +-- returns: STATIC_INSTRUCTIONS + "\n\n" + recallSnippet
                        v
                appendPrompt -> {{appendPrompt}} in template -> base system prompt
                                                              -> /dump (done)
                                                              -> LLM context (done)

agent_end
    +-- mmemory-extension.ts agent_end
            +-- drainPendingConsolidation() -> LLM consolidation call -> obs queue file
            +-- maybePollConsolidation() -> next poll fetch
```

### Rules injection detail

Rules reach the system prompt via `src/capability/rulebook*` pipeline:
1. All rule files in the workspace are discovered by path-glob matching against the current working directory and open files
2. Matching rules are deduplicated by precedence (deeper path wins)
3. Passed as `rules: RuleEntry[]` to `BuildSystemPromptOptions`
4. Template renders them as `- name (globs): description` list in `{{#each rules}}` block
5. Rules are path-scoped  -  they only appear when working in their glob-matched directories

Rules are NOT extension-accessible. They are computed in `sdk.ts` and baked into the static prompt.

### Known issues / future work
- **Double executeMemoryBuild**: both `mmemory-backend.ts start()` and `mmemory-extension.ts session_start` call `executeMemoryBuild`. Redundant, harmless (server deduplicates). Fix: remove from extension session_start once backend is the canonical init path.
- **State coupling**: backend reads from extension's `sessionMap` via `getMmemorySessionState`. If extension not running, backend returns no memories. Long-term: backend should own state, extension should only handle lifecycle events (retain, agent_end).

## Tool Description Design Decisions

> Decisions made and problems avoided in designing the three mme-*.tool-desc.md sidecars.

### Three tools only: retain / recall / reflect
**Decision**: Gateway tool removed. Consolidate tool never exposed to LLM.
**Problem avoided**: Gateway added dispatch ambiguity  -  LLM had to infer the right sub-operation from user phrasing. Each tool now has a single clear responsibility with explicit trigger conditions in its sidecar. Consolidation is server-owned (watermark-based); exposing it as a tool would let the LLM decide timing, creating race conditions and duplicate observations.

### recall and reflect route to panel only  -  LLM receives `<-`
**Decision**: Both tools emit `SCHEDULE_SLASH_CHANNEL` -> slash handler -> `showMPanel`. LLM is never given the recall results as tool output.
**Problem avoided**: Returning recall results to the LLM risks confabulation  -  the LLM acts on stale or mismatched memories as if they were current facts. The panel-only pattern keeps memories as passive background that the user can inspect without polluting the LLM's reasoning context.

### Trigger conditions live in tool descriptions, not in extension intercepts
**Decision**: `.recall`, `.reflect`, `.retain` triggers are defined in `mme-*.tool-desc.md`. No `startsWith(".recall")` intercept in the extension.
**Problem avoided**: Prefix matching is brittle  -  it misses `.rec`, `memory recall`, mid-sentence variants, and natural-language equivalents. The LLM handles all variants because the tool description teaches them. This is the same pattern as `mreview` (100% LLM-driven, no extension intercept).

### retain content appends to session chunk, does not replace
**Decision**: The `content` argument becomes a `**Note:**` section appended to the retained session transcript. It does not create a standalone note file.
**Problem avoided**: A standalone note loses the conversational context that gives it meaning. A note saying "use JWT" is ambiguous; the same note embedded in the session where the decision was made is self-contained and searchable with full context.

### executeManualRetain bypasses N-turns gate unconditionally
**Decision**: `/mmm retain` and the `mmemory_retain` tool both call `executeManualRetain` which ignores `retainEveryNTurns`.
**Problem avoided**: A cadence gate silently ignoring an explicit user instruction (`.retain`) is a trust violation. Explicit user intent must be honored immediately. The gate is for autonomous operation; explicit commands override it.

### mme-injection-preamble.md is the system prompt injection sidecar
**Decision**: `buildDeveloperInstructions` in `mmemory-backend.ts` loads content from `mme-injection-preamble.md` via `createSidecar`. Nothing is hardcoded in TypeScript.
**Problem avoided**: Hardcoded strings in backend code are invisible to post-deploy customization. The sidecar pattern makes the injection content editable without a rebuild, consistent with all other m-family text.

### mme-recall-preamble.prompt.md is for the recall tool routing only
**Decision**: The preamble sidecar drives the panel-routing behavior description for `mmemory_recall`. It is NOT injected into the system prompt.
**Problem avoided**: Mixing system-prompt guidance with tool-routing guidance in the same sidecar creates confusion about which content goes where and makes both harder to maintain.

## `get_injection_snapshot`  -  Dedicated Injection Endpoint

> Designed 2026-05-09. Replaces `executeMemoryRecall(mode="session")` for system prompt injection.

### Why a dedicated endpoint
Injection is NOT a recall/search operation. It is a deterministic time-ordered snapshot:
"give me the N most recent sessions, the K nearest observations before the session window, and M most recent files."
No BM25, no vector search, no ranking. Conflating injection with recall via `mode="session"` was wrong  - 
different semantics, different tuning, different failure modes.

### Request
```json
{
  "action": "get_injection_snapshot",
  "project_dir": "<config.storageRoot>",
  "project": "<config.projectLabel>",
  "session_limit": 5,
  "observation_limit": 3,
  "file_limit": 5,
  "max_chars": 8000
}
```
Note: `project_dir` locates `chunks.json`; `project` filters chunks by the `project` metadata field
(one `chunks.json` shared across projects  -  filter required).

### Server algorithm
```
1. sessions      = chunks WHERE project=P AND source=session
                   ORDER BY ts DESC LIMIT session_limit
                   -> reverse to ts ASC

2. anchor_ts     = min(ts) across selected sessions  (0 if empty)

3. observations  = chunks WHERE project=P AND source=observation AND end_ts < anchor_ts (strict)
                   ORDER BY end_ts DESC LIMIT observation_limit
                   -> reverse to ts ASC

4. files         = chunks WHERE project=P AND source=file
                   ORDER BY ts DESC LIMIT file_limit
                   -> reverse to ts ASC

5. Safety net: if total_chars(sessions + observations + files) > max_chars:
       drop sessions[-1] (newest) until under budget
       observations and files are NEVER dropped
```

### Response
```json
{
  "sessions":      [{"text": "...", "ts": 123, "end_ts": 123}],
  "observations":  [{"text": "...", "ts": 123, "end_ts": 456, "date": "YYYY-MM-DD"}],
  "files":         [{"text": "...", "ts": 123, "path": "...", "action": "read|written|modified"}],
  "anchor_ts":     123
}
```

### Config keys (new `mmemory.injection` namespace)
```yaml
mmemory:
  injection:
    sessionLimit:      5    # N most recent session chunks
    observationLimit:  3    # K nearest observations before session window (oldest->newest)
    fileLimit:         5    # M most recent file chunks
    maxChars:          8000 # safety net  -  drop newest sessions only if exceeded
# Observation cardinality: one observation per consolidation call (one LLM call = one observation)
# covering the full submitted chunk window: ts=min(chunk.ts), end_ts=max(chunk.ts)
# The LLM prompt enforces character limit via {{maxObservationChars}} substitution
```

### Client changes
- `mmemory-backend.ts` `start()` and `beforeAgentStartPrompt()` call `get_injection_snapshot` instead of `executeMemoryRecall`
- New `formatInjectionSnapshot(response)` function builds `<observations>` + `<memories>` + `<referenced_files>` blocks directly from the structured response  -  no `RecallResult` intermediary needed
- `executeMemoryRecall` remains for user-driven `.recall` / `.reflect` (BM25+vector, unchanged)
