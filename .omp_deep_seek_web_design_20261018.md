## 2. How search works in OMP (all refs verified 2026-10-18)

### 2.1 Pipeline

Entry: builtin tool `web_search` (`BUILTIN_TOOL_NAMES` at `packages/coding-agent/src/tools/builtin-names.ts:24`). Execution lives in `packages/coding-agent/src/web/search/index.ts`:

- `executeSearch` (:168-338) resolves the role chain: `roleCandidatePool("web", settings, modelRegistry)` → `resolveRoleChain("web", ...)` or an explicit `params.model` (:175-183).
- For each candidate: if catalog kind is `search` → `getSearchProvider(model.id)` (:225-226); else if `model.webSearch` → `getGroundedSearchProvider(model.webSearch)` (:227-228); else skip.
- Availability gate (:233-242): `provider.isAvailable(authStorage, model)` (skip candidate) vs `isExplicitlyAvailable` (fail loudly when explicitly selected).
- Provider call builds the full `SearchParams` (:246-264). Failures accumulate into a user-facing fallback summary (`formatSearchProviderFailures`, provider.ts:79-84).
- Role/kind rule: `packages/coding-agent/src/config/model-roles.ts:48` — `kind === "search" || (kind === "chat" && model.webSearch !== undefined)`.

### 2.2 Provider registries (closed, core-internal)

`packages/coding-agent/src/web/search/provider.ts`:
- `PROVIDER_LOADERS` (:18-39) — 20 pure engines: `perplexity, zai, exa, tinyfish, jina, kagi, tavily, firecrawl, brave, kimi, parallel, synthetic, ollama, searxng, duckduckgo, google, ecosia, startpage, mojeek, public`.
- `GROUNDED_PROVIDER_LOADERS` (:41-48) — 6 grounding backends: `gemini, anthropic, codex, xai, openrouter, openai`.
- Instances memoized per id (:50-59). `isRegisteredSearchEngine` (:87-89) checks `PROVIDER_LOADERS` only; `getSearchProvider` (:92-95) rejects unknown ids; `getGroundedSearchProvider` (:98-100).

### 2.3 Provider contract and types

- `providers/base.ts`: `SearchParams` (:17-83) — `query`, `parsedQuery` (StructuredQuery), `limit`, `recency`, `systemPrompt`, `signal`, `timeoutMs`, `authStorage` (**the only credential source a provider may consult**, :10-16, :66-67), `model` (catalog Model), `thinkingLevel`, `modelRegistry`, `explicit`, `sessionId`, plus Gemini-specific knobs. `SearchProvider` abstract class (:85+).
- Unified types: `packages/tui/src/tools/web-search-types.ts` — `SearchProviderId = keyof typeof SEARCH_PROVIDER_LABELS` (:42, **closed string-literal union**), `getSearchProviderLabel` falls back to raw id (:45-47), `SearchSource` (:50-57: `title, url, snippet?, publishedDate?, ageSeconds?`), `SearchResponse` (:79-92: `provider | "none"`, `answer?`, `sources`, `citations?`, `searchQueries?`, `relatedQuestions?`, `usage?`), `SearchCitation`, `SearchUsage`.
- Re-exported into search namespace by `web/search/types.ts` (:1-4).

### 2.4 Query parsing

`web/search/query.ts` — `parseSearchQuery(query) → StructuredQuery` (directives: `site:`, `-site:`, `-`, `"..."`, `lang:`, `after:`, `before:`). Example mapping onto an upstream API: `providers/anthropic.ts:69-103` (`site:` → `allowed_domains`, `-site:` → `blocked_domains`, mutually exclusive; directive-free queries pass through byte-identical).

### 2.5 Grounding axis is catalog-only (key constraint)

- `Model.webSearch?: WebSearchGrounding` — `packages/catalog/src/types.ts:47` (union `"gemini"|"anthropic"|"codex"|"xai"|"openrouter"|"openai"`), field on `Model` interface (:1497-1500, also `webSearchModel`).

### 2.6 Catalog seed for `web/*` engines

`packages/catalog/src/compat/rules/providers/web.kdl` — `provider "web"` seed block, one `model "<id>"` per engine (cost all 0, `supports-tools #false`), trailing `models "*" { kind "search" }` (:158-160). Adding an engine id requires a seed entry + regen: `bun run gen:compat` (documented `compat/rules/README.md:21`; compiles `rules/` → `src/compat/rules.json`, committed).

### 2.7 Anthropic grounded provider — protocol reference for DeepSeek Messages mode

`providers/anthropic.ts`:
- Server tool constants: `WEB_SEARCH_TOOL_TYPE = "web_search_20250305"`, name `web_search` (:50-51).
- `callSearch` (:138-215): URL = `buildAnthropicUrl(auth)` where auth is built from **`params.model.baseUrl`** (`searchAnthropic` :336-339 — `buildAnthropicAuthConfig(key, params.model.baseUrl, ...)`); body = `{model: model.id, max_tokens, messages:[{role:"user",content:query}], tools:[{type, name, allowed_domains?, blocked_domains?}], metadata?, temperature?, system?}`; headers via `buildAnthropicSearchHeaders` (Claude-Code injection can be disabled per-model via `compat.injectClaudeCodeInstruction === false`, :160-163).

## 3. DeepSeek search capability (verified specs)

### 3.1 Raw Search/Fetch API — RECOMMENDED engine backend

Source: https://api-docs.deepseek.com/guides/search (fetched 2026-10-18; guide also links `/api/search` and `/api/fetch` reference pages, not individually fetched). GA announcement: https://api-docs.deepseek.com/news/news261017.

- Endpoints: `POST https://api.deepseek.com/v1/tools/search`, `POST https://api.deepseek.com/v1/tools/fetch`. Bearer auth: `Authorization: Bearer <DEEPSEEK_API_KEY>` + `Content-Type: application/json`. Errors follow the OpenAI error format (`{error:{message,type,param:null,code}}`).

Search request:

| Field | Type | Req | Default | Notes |
|---|---|---|---|---|
| `query` | string | yes | — | 1–128 Unicode chars; supports `site:` `site:a OR site:b` `-site:` `-term` `-"phrase"` `"phrase"` `lang:zh,en` `after:YYYY` `before:YYYY` |
| `count` | int | no | 10 | 1–50 |
| `ori_question` | string | no | — | ≤128 chars, original user question; `null` = not provided; harness 2026-10-16 probes showed no measurable effect |
| `localization` | string | no | `""` | IP address for localization |
| `need_content` | bool | no | false | full page content in `content`; keep `false` for the engine |

Search response: `{results: [...]}`; empty array = valid success. Item fields: `rerank_score` (0–3, ≥1.5 high quality), `title`, `url`, `snippet` (100–200 chars), `summary` (600–800 chars), `content` (empty unless `need_content`), `site_name`, `site_icon`, `date` (RFC 3339 or null), `authority` (0–4, -1 unknown).

Fetch request: `{url}` (≤8192 chars, http/https, no userinfo) → `{title, content}` (content = Markdown). HTTP 404 when no usable content; harness probe observed HTTP 500 in that case on 2026-10-16.

Errors: 400 invalid, 401 auth, 402 balance, 403 fetch policy, 404 no content, 408 timeout, 413 too large, 429 QPS, 500/504 downstream. Retry only 408/429/5xx. **No automatic retry in the harness adapter — match that.**

Billing: $0.75 per 1,000 successful requests, each API billed independently; a request is billable only on HTTP 200 with results/content; `count` does not affect price. Server-side tool calls through DeepSeek Harness / Claude Code / Codex are free until 2026-11-01 00:00 Beijing; direct API calls follow the same start date.

Rate limits: account-level, **5 QPS Search, 5 QPS Fetch** (independent quotas; Fetch also has a per-domain QPS limit). 429 above.

### 3.2 Anthropic-compatible Messages mode (rejected for OMP)

Source: local harness clone `packages/web/web-search-deepseek/{README.md,src/provider.ts,src/types.ts}`.

- `POST https://api.deepseek.com/anthropic/v1/messages` (config `$DEEPSEEK_SEARCH_BASE_URL`, independent of chat `$DEEPSEEK_BASE_URL`), model `deepseek-v4-flash`, `anthropic-version: 2023-06-01`, sends key as both `x-api-key` and `Authorization: Bearer`, `thinking: {type:"disabled"}`, native server tool `web_search` with `max_uses` (default 5).
- Response parsed from `web_search_tool_result` blocks (`url`,`title`,`page_age`) + `cited_text` joins; text blocks arrive WITHOUT `citations`; no result-count knob (post-hoc truncation only).
- Cost: **one full Messages model turn per search** (latency + generated tokens). This is why the harness keeps it default only until the Search API launch.

### 3.3 Ready-made adapter to port (raw API)

Local harness clone `packages/web/web-deepseek-api/`: `src/index.ts` (plugin/settings), `src/search.ts` (Search provider, validates response JSON), `src/fetch.ts` (Fetch provider), `src/transport.ts` (credential resolution, cancellation, redirect rejection, failure guidance). Constants there: `DEEPSEEK_WEB_API_BASE_URL = "https://api.deepseek.com/v1/tools"`. Behaviors worth copying: empty results = success; fetch answers 200 with Markdown and reports the requested URL (API exposes no final redirect URL; redirects are rejected pre-flight); account-token header `x-dsh-auth-token` (DeepSeek-account integration — NOT needed for OMP).

## 5. Extension feasibility (public/private; does open_sdk help?)

### 5.1 What the extension API offers today (public surface)

`packages/coding-agent/src/extensibility/extensions/types.ts`:
- `registerTool` (:1690) — LLM-callable tool with own schema + renderer (`ToolDefinition` :849-926).
- `registerProvider` (:1918) — **chat LLM providers only**: `ProviderConfig` (:1937-1981: baseUrl, apiKey, api, custom `streamSimple`, headers, models, oauth, fetchDynamicModels), `ProviderModelConfig` (:1984-2016: id, name, api, kind, reasoning, thinking, input, cost, contextWindow, maxTokens, headers, compat) — **no `webSearch` field** → cannot attach grounding.
- Events (`on(...)` :1613-1683), commands/shortcuts/flags, UI, `pi.openSdk` namespace (:1606-1607).

### 5.2 Hard limits (verified absent)

- No extension seam in the search provider registries (`provider.ts:18-48` is a closed const; nothing consults extensions).
- No way to add a `providers.fetch` enum value from an extension.
- Grounding cannot be attached to any model from extension code (§2.5).

### 5.3 Tool shadowing (makes pure-extension delivery possible but unattractive)

An extension tool registered under a builtin name shadows the builtin: "the agent loop routes exact-name matches ahead of wire aliases — a registered non-built-in tool with that name wins" (`session/session-tools.ts:657-674`; registration itself `extensibility/extensions/loader.ts:220-226` Map set by name). Shadowing `web_search` would force re-implementing the whole pipeline (role chain, query parsing, availability, fallback summary, TUI native rendering) inside the extension. NOT recommended.

### 5.4 Does open_sdk help?

Current open_sdk exports (OPEN-SDK.md): `complete/completeSimple/streamSimple`, `resolveRoleSelection`, `settings`, `applyOverrides`, `dispatchSlashCommand`, pi-ai internals (Bedrock, stream utils), TUI helpers. For the **raw-API** engine none of these are needed — it is a plain HTTPS POST. The missing piece is the **registration seam**: nothing exports `SearchProvider`/types/query-parsing, and nothing lets an extension inject an engine. That is exactly the kind of gap the fork exists to close (OPEN-SDK.md §Adding more exports: add export lines to `open-sdk.ts`; keep the fork ONE commit).

## 6. open_sdk fork amendment (Option D, exact design) — RETAINED AS DESIGN NOTE ONLY, not needed for DeepSeek

### 6.1 Core hook — `packages/coding-agent/src/web/search/provider.ts` (additive, ~15 lines)

After `GROUNDED_PROVIDER_LOADERS` / near `providerInstances` (:50):

```ts
/** open-sdk seam: engines registered by extensions, consulted before built-ins. */
const extensionEngines = new Map<string, ProviderLoader>();

export function registerSearchEngine(id: string, loader: ProviderLoader): void {
	extensionEngines.set(id, loader);
	providerInstances.delete(id); // allow live re-registration

```

Patch the two resolvers:

```ts
// isRegisteredSearchEngine (:87-89)
return Object.hasOwn(PROVIDER_LOADERS, id) || extensionEngines.has(id);

// getSearchProvider (:92-95)
const extensionLoader = extensionEngines.get(id);

return loadProvider(id, PROVIDER_LOADERS[id]);
```

## 7. Extension implementation spec — `omp-extensions-private/extensions/deepseek-web/` (SEARCH engine parts SUPERSEDED by upstream `53d6d1d689`; only the `web_fetch` tool — 7.1 `fetch.ts` bullet, 7.2, 7.3 live smoke — remains candidate work)
