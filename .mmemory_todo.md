## Architecture (locked decisions)

- Consolidation input: `source:turn` chunks since `last_obs_end_ts` (count-based, NOT time-based; "session" -> "turn" throughout)
- Fact extraction (`executeMemoryExtract`) eliminated
- Three source types: `session`, `observation`, `file`
- `end_ts` on ALL chunk types for universal time-range queries:
  - `session` / `file`: `end_ts = ts` (point-in-time — set by server on ingestion)
  - `observation`: `end_ts = max(turn.ts)` across the consolidated window (set by TypeScript, not LLM)
- Watermark: `max(end_ts)` across project's `source:observation` chunks — O(n_project_chunks) in-memory over cached project chunks; acceptable at mmemory scale (hundreds–low-thousands)
- Client holds NO consolidation state; server computes watermark from in-memory chunk cache on each `get_consolidation_chunks` call
- Client trigger: on each retain completion, check `now > lastPollAt + consolidationPollIntervalMs`; if yes -> poll server
  -> server returns turn chunks if `count >= threshold`, else `[]`; "at-least" semantics
- Force consolidation (`/mmemory consolidate`): same API, `threshold:1`
- Race condition (two agents): accepted — near-duplicate observations, harmless, no lock (stale lock files on crash are worse)
- Consolidation runs as non-awaited async Promise (TypeScript) — dies with main process; lower priority via fire-and-forget
- Queue writes use single buffer flush (`write_text` / single `f.write`) — atomic at queue file sizes (KB range); no temp+rename needed
- LLM outputs `{observation, entities, date}` ONLY — TypeScript computes `start_ts`/`end_ts` from input chunks; no LLM timestamp hallucination
- Cap: `consolidationMaxTurns` limits turn chunks passed to LLM; 20k char truncation is secondary safety net
- `<observations>` injected ABOVE `<memories>` (chronological: older obs -> newer session turns); revisit after testing
- All tool writes go through queue via slash command handler — single write path per operation
- One consolidation prompt sidecar: `mme-consolidation.prompt.md` (system prompt; turn chunk texts constructed in code)
- All m-family prompt/description text is sidecar-managed (user-editable post-deploy)
- core `MEMORY.md` / `memory_summary.md` = separate system, do NOT touch
