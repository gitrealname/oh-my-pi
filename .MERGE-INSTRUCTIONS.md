# AWS-CORP Merge Instructions (version-agnostic)

This file is the permanent rulebook for merging upstream `oh-my-pi` releases into the
`aws-corp` branch. It is version-agnostic: the procedure and rules apply to every merge.
For version-specific details (what upstream changed, how conflicts were resolved, what
actually happened) see `merge_vNN.NN.NN.md` committed in the repo for that merge.

**This file is gitignored (dot-prefix). It lives locally only.**  
Update it whenever a correction or new lesson is learned — if a correction is generic, it
belongs here, not only in the version-specific file.

---

## Hard Rules — Read Before Touching Anything

> **STOP. Before any action, show the full plan and wait for explicit user approval.**
> Do not create branches, do not run git merge, do not resolve conflicts, do not build,
> do not commit, do not push — until the user says so for each individual step.
> Approval in one turn does NOT carry to the next turn.

1. **Never commit or merge without explicit per-turn user instruction.** Completing a
   step does not imply permission to proceed to the next step.

2. **Never `git stash apply`.** Has broken the project before. If stash is involved,
   stop and discuss.

3. **Never `git checkout -- .`** without explicit instruction. Discards working-tree
   changes silently.

4. (cut by user)

5. **Never build with `--build-native`** unless Rust code changed. Default `build.cmd`
   skips native and is the correct default.

6. **After any conflict resolution, typecheck before building.** `bun tsc --noEmit`
   must be zero errors before `build.cmd` is run. Do not skip this.

7. **After merging, verify every AWS-CORP change is still present** (see checklist
   below) before declaring the merge done. Do not rely on memory.

8. **Present proposed conflict resolutions before applying them.** Show what upstream
   has, show what we have, show the proposed merged result — then wait for approval.

**Why here and not `corp-sdk-extensions.ts`:** `completeSimple` must be re-exported from

The corp-sdk-extensions pattern is for internal wiring, not external re-exports.

### 3. `extensibility/extensions/runner.ts` — `executePython` removed
`executePython` REMOVED from `createCommandContext()`. Matches item 2.

### 4. `modes/interactive-mode.ts` — `waitForInputReady()`
SCHEDULE_SLASH timing fix. Three insertion points, all marked `// AWS-CORP`:

**Class field (with other private fields):**
```typescript
// AWS-CORP: waitForInputReady
#inputReadyResolvers: (() => void)[] = [];
```

**Class method:**
```typescript
// AWS-CORP: waitForInputReady — resolves after getUserInput() arms onInputCallback
waitForInputReady(): Promise<void> {
    if (this.onInputCallback) return Promise.resolve();
    return new Promise<void>(resolve => {
        this.#inputReadyResolvers.push(resolve);
    });
}
```

**Inside `getUserInput()`, where `onInputCallback` is set:**
```typescript
for (const r of this.#inputReadyResolvers.splice(0)) r();
```

**SCHEDULE_SLASH subscription (inside constructor event subscriptions):**
```typescript
if (command) void this.session.waitForIdle()
    .then(() => this.waitForInputReady())
    .then(() => { this.editor.onSubmit?.(command); });
```

**Why `waitForInputReady()` and not `waitForIdle()`:**
`waitForIdle()` resolves when `isStreaming=false` — but `onInputCallback` may not be set
yet at that point. `getUserInput()` (which arms `onInputCallback`) is called slightly after
`waitForIdle()` resolves. Using `waitForIdle()` alone loses the injected command. The real
gate is `onInputCallback` being non-null.

### 5. `extensibility/skills.ts` — path normalization

// AWS-CORP: normalize to forward slashes for cross-platform skill paths
const metaLines = [`Skill: ${skill.filePath.replace(/\\/g, "/")}`];

### 9. mtuicontrol RPC files — wholesale additions
These files have no upstream counterpart. Upstream will never touch them. Verify they are
unmodified after merge via `git diff v_PREV HEAD -- <file>`:
- `modes/rpc/rpc-inject.ts`
- `modes/rpc/rpc-inject-handler.ts`
- `modes/rpc/rpc-inject-client.ts`
- `extensibility/extensions/m-mtuicontrol-extension.ts`

### 10. `slash-commands/builtin-registry.ts` — custom slash commands
`/mmemory`, `/mprune`, `/mreview` commands registered with `handleTui:` (NOT `handle:`).

**Critical — learned the hard way in v15.0.0 merge:**
v15.0.0 split the unified runtime into `SlashCommandRuntime` (ACP/RPC, no `.ctx`) and
`TuiSlashCommandRuntime` (interactive, has `.ctx`). All three of our commands use
`runtime.ctx.sessionManager`, `runtime.ctx.showStatus()`, `runtime.ctx.chatContainer`, etc.
They MUST use `handleTui:`. Using `handle:` compiles without error but crashes at runtime
with `TypeError: undefined is not an object (evaluating 'runtime.ctx.sessionManager')`.

### 11. `main.ts` — `--no-memory` must use `settings.override`, not `settings.set`
**Critical — learned the hard way in v15.0.0 merge:**
`settings.set("mmemory.enabled", false)` persists to disk — silently disables mmemory
in `config.yml` for all future sessions. `settings.override(...)` is session-scoped only.
The `--no-memory` flag MUST use `override`. Verify this is correct after every merge.
If it ever reverts to `settings.set`, run a session, exit, then inspect `config.yml` to
confirm `mmemory.enabled` was not written.

## Known Pitfalls (burn-in lessons from past merges)

### `bun.lock` conflict markers
`bun.lock` is a large generated file. Conflict markers inside it are NOT always caught by
`git status` as unresolved — they silently remain as literal text and cause `bun install`
to fail with cryptic errors. After resolving conflicts, always grep:
```
grep -c "<<<<<<" bun.lock
```
Should be 0. If non-zero, manually resolve and re-run `bun install`.

### `dist/` vs `binaries/` deploy path split
`bun run build` (inside `packages/coding-agent/`) writes to `dist/omp.exe`.
`deploy.cmd` reads from `binaries/omp-aws-corp.exe`. Deploying `dist/omp.exe` directly
installs the WRONG file. Always go through `build.cmd` (root script) which posts to both.

### `rpc-client.ts` field renames across upstream versions
Upstream has renamed fields in `RpcSessionState` across versions (e.g., `streaming` →
`isStreaming` in v15.0.0). Our mtuicontrol code references these fields. After each merge,
check `rpc-client.ts` for type errors around `state.*` fields.

### `Parameters<typeof this.#send>` is invalid TypeScript
Private class field method references cannot be passed to `Parameters<>`. Replace with
the explicit type alias (`RpcCommandBody`). This was a pre-existing bug in our code
surfaced by v15.0.0's stricter type checking.

### `normalizePlanTitle` → `resolvePlanTitle` (v15.2.4+)
Starting in v15.2.4, `normalizePlanTitle` was renamed to `resolvePlanTitle` and its
signature changed to `{ suppliedTitle, planContent, planFilePath }`. If interactive-mode.ts
has a call site to the old name, it will fail tsc.

### `bun.lock` version refs during merges
During the v15.0.0 merge, two stale lockfile entries remained:
`@bufbuild/protoplugin/typescript@5.4.5` and a stale version ref. When upstream drops a
dependency, the lockfile merge leaves ghost entries. After `bun install` succeeds, check
`bun.lock` diff for any entries referencing the OLD version number.

### `build.cmd` flags must stay in sync with `build-binary.ts`
If upstream adds new `bun build --compile` flags to `build-binary.ts`, they must also be
added to `build.cmd`. These diverged in v15.0.0. After merging, compare the compile
invocation in `build-binary.ts` with the one in `build.cmd`.

### Graphify extension: never import `@oh-my-pi/*` directly
The graphify extension (`index.ts` deployed to `.omp-work/agent/extensions/graphify/`)
must NEVER import from `@oh-my-pi/*` directly. Use `pi.pi.*` only. Direct imports break
because the package resolution context inside a deployed extension is the OMP binary,
not the graphify source tree.


### Native addon version sentinel changes (v15.2.4+)
Starting in v15.2.4 the binary validates a version sentinel (`__piNativesV15_2_4`) in the
`.node` file and looks for it at a versioned path `~/.omp/natives/<version>/`.
If the sentinel doesn't match, OMP crashes immediately on startup with:
```
does not expose the @oh-my-pi/pi-natives@15.2.4 version sentinel
```
**Pre-merge check:** look at `packages/natives/package.json` — if the version changed,
`deploy.cmd` must copy `.node` files to the new versioned path. Verify `deploy.cmd`
reads the version dynamically (it now uses `python3` to read `package.json`).
**Always run `build.cmd --build-native` after a merge** — never skip it.

### `--build-native` is mandatory after any merge that touches `packages/natives/`
Skipping it leaves a stale `.node` with the wrong sentinel. The binary will crash.
Check `packages/natives/package.json` version in the diff — if it changed, native rebuild
is required. If unsure, always rebuild; it costs ~4 minutes but prevents a silent breakage.

### `settings-schema.ts` silently drops our spreads on auto-merge
Our three imports + spreads (`MMEMORY_SCHEMA_ENTRIES`, `PRUNE_SCHEMA_ENTRIES`,
`SCRIPT_SCHEMA_ENTRIES`) live at the top and bottom of `settings-schema.ts`. Upstream
heavily modifies this file every release. The auto-merge consistently drops our additions
because they're at conflict boundaries. **Always verify after merge:**
```
grep -c 'MMEMORY_SCHEMA_ENTRIES\|PRUNE_SCHEMA_ENTRIES\|SCRIPT_SCHEMA_ENTRIES' \
  packages/coding-agent/src/config/settings-schema.ts
# Must return 6 (3 imports + 3 spreads)
```
Add to the post-merge verification checklist.

### Test: `acp-agent.test.ts` skill path assertion
Our `skills.ts` normalizes `skill.filePath` to forward slashes. The test at line ~1127
uses the raw `skillPath` (Windows backslashes). After any merge that touches `skills.ts`
or the test, verify the assertion uses `.replace(/\\\\/g, "/")`:
```typescript
expect(...).toContain(`Skill: ${skillPath.replace(/\\/g, "/")}`);
```

## Merge Procedure (every version)

### CRITICAL: upstream tag lineage can be non-linear — check before doing ANYTHING

`v15.0.0 → v15.1.3` is linear (one descends from the other). `git merge` works cleanly.
`v15.1.3` and `v15.2.4` are on **divergent upstream branches** — common ancestor is from
January 2026, four months before either tag. `git merge v15.2.4` on `aws-corp` produces
256 add/add conflicts because git sees almost every file as independently added by both sides.

**TRIPWIRE: if `git merge` produces more than ~15 conflicts, STOP.**
```
git merge --abort
```
Diagnose the lineage first. Do not touch a single conflict file until you understand why.

### Step 0: Check merge base linearity
```
git merge-base aws-corp vNN.NN.NN
git log --oneline -1 $(git merge-base aws-corp vNN.NN.NN)
git merge-base --is-ancestor vPREV vNN.NN.NN && echo LINEAR || echo NON-LINEAR
```
- **LINEAR**: proceed with Strategy A
- **NON-LINEAR**: proceed with Strategy B

**Show the result to the user and confirm strategy before doing anything else.**

### Pre-merge checklist
- [ ] All three repos clean: `git status` empty in `.oh-my-pi`, `.graphify`, `D:/.ai`
- [ ] Latest upstream fetched: `git fetch origin`
- [ ] Merge base checked — linearity confirmed, strategy chosen, user approved
- [ ] `merge_vNN.NN.NN.md` written (version-specific plan)
- [ ] **User has approved branch creation**

---

### Strategy A — LINEAR merge (`git merge`)

```
git checkout aws-corp
git checkout -b merge/vNN.NN.NN
git merge vNN.NN.NN
```

**Resolve conflicts with full knowledge of aws-corp — no `--theirs`, no `--ours` shortcuts.**

For every conflicting file:
1. Read what upstream changed (their side) and what aws-corp has (our side)
2. Understand the intent of both changes
3. Produce the correct merged result: upstream's changes + our AWS-CORP additions preserved
4. Files with no `// AWS-CORP` markers that conflict on add/add: upstream version is correct
5. Present proposed resolution, wait for approval, apply

The only acceptable bulk shortcut: `git checkout --theirs` on files confirmed to have
zero AWS-CORP markers AND where our only "change" is adding the file that upstream also added.
For any file that has `// AWS-CORP` markers: always resolve manually, line by line.

---

### Strategy B — NON-LINEAR: branch from aws-corp, resolve 256 conflicts correctly

Despite the large conflict count, the correct approach is **still `git merge` from aws-corp**,
not branching from upstream. The v15.2.4 merge confirmed this: branching from upstream and
patching our changes in produced a diff with 174 unexpected additions vs aws-corp.
The correct shape is `merge/vNN.NN.NN` diverges from `aws-corp` only by the upstream delta.

```
git checkout aws-corp
git checkout -b merge/vNN.NN.NN
git merge vNN.NN.NN   # expect ~256 add/add conflicts with non-linear tag
```

**Build the AWS-CORP file set first**, then resolve:
```python
# Before touching any conflict — build the complete exclusion list
import subprocess
r = subprocess.run(['git','grep','-l','AWS-CORP','aws-corp','--','packages/'],
    capture_output=True, text=True)
aws_corp_files = set(l.replace('aws-corp:','') for l in r.stdout.strip().split('\n') if l)
# v15.2.4: 44 files — this list grows as we add features; always regenerate fresh
```

**Resolution rules:**
- Files NOT in `aws_corp_files` + conflict is add/add (both sides added the same new file):
  `git checkout --theirs -- <file> && git add <file>` — upstream version, we never touched it
- Files IN `aws_corp_files`: resolve manually, line by line. No bulk shortcuts.
  For each conflict hunk: take upstream as structural base, preserve our `// AWS-CORP` additions
- Files with only stage 2 (no stage 3): `git checkout --ours` — our additions, no upstream counterpart

```python
# Bulk-resolve non-aws-corp files only
r = subprocess.run(['git','diff','--name-only','--diff-filter=U'], capture_output=True, text=True)
theirs = [f for f in r.stdout.strip().split('\n') if f and f not in aws_corp_files]
# Split by stage availability, take theirs/ours accordingly
# Then handle the aws_corp_files manually, one by one
```

After bulk resolution: **verify diff vs aws-corp is only upstream additions/modifications.**
```
git diff --name-status aws-corp merge/vNN.NN.NN | grep "^A" | wc -l
# Should equal the number of genuinely new files upstream added (e.g. 36 for v15.2.4)
# Zero is wrong (lost something). 174 is wrong (inverted the merge).
```

### Step: Typecheck (both strategies)
```
cd packages/coding-agent
bun tsc --noEmit --project tsconfig.json 2>&1 | grep "error TS"
```
Zero errors required. Fix before proceeding. Common post-merge tsc failures:
- **Settings schema spread missing:** `settings-schema.ts` must import and spread
  `MMEMORY_SCHEMA_ENTRIES`, `PRUNE_SCHEMA_ENTRIES`, `SCRIPT_SCHEMA_ENTRIES`
- **Upstream API renames:** e.g. `normalizePlanTitle` → `resolvePlanTitle` in v15.2.4
- **Interface changes:** upstream removed or renamed fields our code references

### Step: Run full build with native
```
D:\.ai\OMP\dist\build.cmd --build-native
```
Required after every merge — the Rust native addon must be rebuilt for tests to pass.
Without `--build-native`, `pi_natives.win32-x64-baseline.node` will be stale and ALL tests
fail with "LoadLibrary failed: not a valid Win32 application" (looks like 360 failures but
is actually one root cause).

### Step: Run test suite
```
cd packages/coding-agent
bun test --timeout 30000
```
Full suite must pass. Pre-existing failures on `aws-corp` are acceptable if confirmed identical
before/after merge (use `git stash` to verify). Merge-introduced failures are blocking.

**m-family tests (always run explicitly):**
```
bun test --timeout 30000 test/mprune-batch.test.ts test/mprune-images.test.ts test/mprune-trim.test.ts test/mprune-stats.test.ts test/mprune-prompt.test.ts test/agent-session-task-abort.test.ts test/task-parallel-abort.test.ts test/script-output-protocol.test.ts
```
These cover our custom aws-corp features. All must pass with zero failures.

**mtuicontrol tests** (`test/mtuicontrol-esc.test.ts`) require a live OMP session — skip in
automated runs, verify manually.

**Pre-existing Windows EBUSY failures** in `settings-manager.test.ts` are environment
noise (file locking on temp dir cleanup). Confirm they're identical on `aws-corp` before
dismissing any `settings-manager` failure.

### Step: AWS-CORP change verification
Go through every item in the Change Registry above. Check off explicitly.


### Step: Deploy and smoke test
```
D:\.ai\OMP\dist\deploy.cmd
D:\.ai\OMP\dist\deploy-graphify.cmd
```
